# WebSocket и Django Channels: теория для перехода `multiplayer` с поллинга на push

Учебный конспект, написанный по вопросам, реально возникшим при разборе конкретной проблемы: HTMX-поллинг `hx-trigger="every 2s"` в `room_detail.html`/`_room_status.html` при росте числа комнат создаёт нагрузку, не пропорциональную реальным изменениям — большинство запросов приходят "проверить, вдруг что-то изменилось" и возвращают то же самое.

Это **теория и план**, код в проекте пока не менялся (сессия от 2026-08-31, дополнено вопросами от 2026-09-01). Когда решите реализовывать — стоит перечитать этот файл ещё раз перед тем, как писать `consumers.py`/`routing.py`, и актуализировать, если что-то в реализации пойдёт не так, как описано здесь (по аналогии с [`FORMS_LEARNING.md`](FORMS_LEARNING.md) — это конспект под конкретный код проекта, не абстрактный туториал).

**Решение по деплою уже принято** (зафиксировано в `quiz_project_plan.md`, Этап 5) — ASGI-сервер в проде будет **Daphne** (не Gunicorn, не Uvicorn), Redis на проде обязателен уже к этому этапу. Здесь остаётся как справочная теория (§11), почему выбор пал именно на Daphne.

---

## 1. Проблема, которую решаем

Каждый открытый `room_detail.html` держит JS-таймер, который каждые 2 секунды делает `GET .../status/`. При N комнатах по 5 игроков это `2.5 × N` запросов в секунду **на весь сайт**, и почти все они — вхолостую (в комнате никто ничего не менял).

Ключевая проблема не в "нагрузке на CPU" — рендер маленького HTML-фрагмента дешёвый. Проблема — в модели воркеров. Проект — синхронный Django (WSGI, вероятно за Gunicorn с `sync`-воркерами). Один такой воркер обрабатывает **один запрос за раз**, блокируясь на всё время запроса, включая ожидание ответа от БД. Если поллинг съедает все воркеры, обычный запрос **другого**, никак не связанного с мультиплеером пользователя встаёт в ту же очередь и "виснет" — воркеры не резервируются отдельно под конкретный вид трафика.

**Порядок величин** (грубая прикидка, не измерено на реальном сервере): при 4 воркерах и ~20-30мс на запрос статуса потолок пропускной способности всего сайта — около 130-160 запросов/сек. Уже около 50-60 одновременно открытых лобби начинают вплотную подходить к этому потолку.

---

## 2. Идея решения: push вместо poll

Сейчас: **клиент** каждые 2 секунды сам инициирует HTTP-запрос — "есть что-то новое?" — и получает ответ, даже если ответ "ничего не изменилось".

С WebSocket: между браузером и сервером один раз открывается **долгоживущее двустороннее соединение** (не HTTP-запрос — специальное "рукопожатие" `Upgrade: websocket`, дальше протокол переключается). Дальше это соединение просто ждёт. **Сервер сам** отправляет данные клиенту в момент, когда что-то реально произошло — и ни разу больше. Холостых запросов не остаётся вообще.

---

## 3. Почему это не "ещё одна вьюха" — ASGI против WSGI

Обычный Django-запрос живёт по протоколу **WSGI**: запрос пришёл → воркер обработал его от начала до конца синхронно → отдал ответ → воркер свободен. Модель заточена под короткие, завершающиеся запросы.

WebSocket-соединение так жить не может — оно не завершается, серверу нужно держать его открытым неопределённо долго **и** уметь отправить данные по собственной инициативе, не дожидаясь входящего запроса. Под это нужен другой протокол — **ASGI** (Asynchronous Server Gateway Interface) — и другой сервер приложения: не Gunicorn (чисто WSGI), а **Daphne** или **Uvicorn**. В проекте `quiz_project/asgi.py` уже существует (Django создаёт его по умолчанию при старте проекта), но пока используется в игрушечном виде — Channels его переиспользует и расширяет.

## 4. Три новых кирпичика Channels

### Consumer — аналог view, но для WebSocket

У view есть `get()`/`post()`. У Consumer — жизненный цикл соединения:

- `connect()` — клиент подключился (аналог начала обработки запроса);
- `receive()` — клиент что-то прислал по сокету (в нашем сценарии, скорее всего, не понадобится — соединение у нас в основном "только на чтение" для клиента);
- `disconnect()` — соединение закрылось (клиент закрыл вкладку, потерял сеть и т.д.);
- плюс произвольные ваши методы-обработчики для событий, которые сервер сам захочет протолкнуть в сокет (см. §6).

### Routing — аналог `urls.py`, но для WebSocket-путей

Отдельный список `websocket_urlpatterns`, сопоставляющий ws-путь (`ws://.../ws/multiplayer/rooms/<code>/`) с классом Consumer — той же механикой, что `path()` в обычном `urls.py` сопоставляет HTTP-путь с view.

### Channel Layer + Groups — то, чего в обычном Django нет вообще

Это ключевая новая концепция и главный источник путаницы, поэтому разберём отдельно и подробно в §7-8.

## 5. Channels — это не отдельное приложение "рядом", а диспетчер на входе

Важно понимать структуру, а не просто "Channels добавляет файлы". `channels` — это библиотека, которая **подменяет диспетчер на самом входе** ASGI-сервера. В `asgi.py` появляется `ProtocolTypeRouter` — первая точка, куда прилетает вообще любое соединение, и она смотрит на **тип**:

```python
# quiz_project/asgi.py (как будет выглядеть; пример, не текущий код)
application = ProtocolTypeRouter({
    "http": django_asgi_app,                      # обычные HTTP-запросы — как раньше, без изменений
    "websocket": AuthMiddlewareStack(
        URLRouter(multiplayer.routing.websocket_urlpatterns)
    ),
})
```

**Ключевой момент**: обычные HTTP-запросы (`/quizzes/menu/`, логин, `room_confirm_ready`, что угодно кроме самого WebSocket-хендшейка) идут по ветке `"http"` напрямую в ваш обычный Django — **routing.py и consumers.py их вообще не касаются**. Эти два файла — не параллельная копия приложения, а отдельная маленькая ветка специально под долгоживущие соединения.

`routing.py` внутри этой ветки играет ровно роль `urls.py`, только сопоставляет ws-путь с классом Consumer, а не HTTP-путь с view-функцией/классом.

## 6. Путь запроса от `new WebSocket(...)` в браузере до вашего кода

```
1. Браузер (JS):  new WebSocket("wss://ваш-домен/ws/multiplayer/rooms/ABC123/")
   → браузер сам отправляет HTTP-запрос с заголовком "Upgrade: websocket"

2. ASGI-сервер (Daphne) принимает запрос,
   видит заголовок Upgrade → трактует соединение как "websocket", а не "http"

3. ProtocolTypeRouter смотрит на тип соединения → отправляет в ветку "websocket"

4. AuthMiddlewareStack — прогоняет через тот же механизм сессий/куки,
   что и обычный Django, и кладёт пользователя в scope["user"]
   (это аналог request.user)

5. URLRouter — сверяет путь "/ws/multiplayer/rooms/ABC123/"
   со списком websocket_urlpatterns из multiplayer/routing.py

6. Найдено совпадение → создаётся экземпляр RoomConsumer,
   вызывается его метод connect()

7. Внутри connect() — ваш код: проверка, что пользователь
   имеет отношение к этой комнате (хост или RoomPlayer,
   тот же смысл, что сейчас в _get_room_context/get_object_or_404),
   регистрация в группе (см. §7), accept()
```

Так что да — `new WebSocket(...)` в JS и есть то, что запускает всю эту цепочку, а `routing.py` — место, где путь сопоставляется с вашим `RoomConsumer`.

## 7. Зачем вообще нужен Redis и что такое "группа"

Проблема, которую решает Channel Layer: у вас несколько **процессов** сервера (не путать с "воркером" в смысле Gunicorn `sync`-воркера — см. поправку про модель Daphne чуть ниже). Конкретное открытое WebSocket-соединение конкретного игрока физически "живёт" в одном конкретном процессе Daphne. Когда что-то меняется (например, кто-то нажал "Подтвердить готовность") — этот `POST` обрабатывается в **своём** процессе как обычная HTTP-вьюха, а уведомить нужно **другие** открытые сокеты, которые физически держат **другие** процессы. Прямой связи между процессами нет — нужен посредник, разделяемый всеми ими. Это и есть **Channel Layer**, в вашем случае — **Redis** (он уже заложен в план стека проекта).

**Важная поправка мысленной модели (вопрос от 2026-09-01): Redis тут ничего не "отслеживает" и не сравнивает состояния.** Он полностью пассивен и не имеет понятия "изменение". Он умеет ровно две операции — обе выполняются только когда их **явно вызывает ваш Python-код**:

1. `group_add(group, channel_name)` — записать в множество "кто состоит в группе".
2. `group_send(group, message)` — прочитать это множество и разложить сообщение по очередям всех перечисленных ящиков.

Если вьюха `room_confirm_ready` изменит `RoomPlayer.is_ready` в БД, но **не вызовет** `group_send` — никто ничего не узнает, сколько бы времени ни прошло: Redis не сравнивает "было/стало" и не заглядывает в БД сам. Правильная мысленная модель — не "сторож, который следит за изменениями", а "почтовое отделение, которое молчит, пока ему не принесли конкретное письмо на отправку". Решение "что-то изменилось, надо разослать" всегда принимает ваш view-код, а не Redis.

**Поправка модели процессов (тот же вопрос):** в отличие от Gunicorn (`sync`-воркер = отдельный процесс, обрабатывает один запрос за раз, блокируясь), Daphne — асинхронный сервер на event loop. **Один** процесс Daphne может держать открытыми одновременно тысячи WebSocket-соединений, не по процессу на соединение. "Несколько процессов", о которых речь выше, — это горизонтальное масштабирование (несколько процессов Daphne за балансировщиком, если один понадобится когда-нибудь разгрузить), а не "по процессу на каждого подключившегося игрока".

Мысленная модель — почтовое отделение с именными ячейками, не "открытие соединения":

- **У каждого открытого WebSocket-соединения есть личное "имя-ящик"** (channel name) — Channels генерирует его автоматически при подключении, что-то вроде `specific.abcXYZ123!q7f8h2`. Это просто уникальный идентификатор одного открытого сокета внутри процесса Daphne, само по себе к Redis отношения не имеющий.
- **Группа — это просто список таких имён-ящиков**, хранящийся в Redis как обычная структура данных (множество). Когда в `connect()` вызывается:

  ```python
  async_to_sync(self.channel_layer.group_add)("room_ABC123", self.channel_name)
  ```

  — это одна операция записи в Redis: "добавь имя-ящик `specific.abcXYZ123!q7f8h2` в множество с ключом `room_ABC123`". Никакого нового соединения на этом шаге не открывается — это строчка в общей "телефонной книге", которую видят все серверные процессы, потому что все они держат одно и то же (постоянное, открытое заранее) соединение к общему Redis — точно так же, как у каждого процесса есть постоянное соединение к БД.

- **Когда что-то нужно разослать** — например, вьюха `room_confirm_ready` в конце вызывает:

  ```python
  async_to_sync(channel_layer.group_send)("room_ABC123", {"type": "room.update", "html": rendered_html})
  ```

  — вот тут Redis реально работает посредником: этот вызов **читает** из Redis множество имён-ящиков, состоящих в группе `room_ABC123`, и для каждого имени-ящика кладёт сообщение в его персональную очередь. Тот процесс Daphne, который физически держит сокет с этим именем-ящиком, "просыпается", забирает сообщение и вызывает у своего живого `RoomConsumer` метод-обработчик (см. §9), который пишет уже в сам WebSocket клиента.

**Итого**: Redis тут — не база данных и не "очередь, которую вы открываете руками", а разделяемая адресная книга + почтовый диспетчер. Он позволяет процессу A (обработавшему обычный `POST` от одного игрока) достучаться до процесса B (который держит открытый сокет другого игрока), хотя они физически друг о друге ничего не знают. Без Channel Layer вьюха в процессе A не имела бы способа "дотянуться" до сокета в процессе B.

## 8. Sync или Async — не обязательно учить asyncio

Проект целиком синхронный (Django ORM без async, `sync` views). Хорошая новость: Channels позволяет писать **синхронные** Consumer'ы:

```python
class RoomConsumer(WebsocketConsumer):   # не AsyncWebsocketConsumer
    def connect(self):
        ...   # обычный синхронный код, обычный Django ORM
```

Внутри Channels сам исполняет такой код в отдельном пуле потоков — писать `async def`/`await` в теле методов не нужно. Асинхронность видна только на границе с Channel Layer (`group_send`/`group_add`) — там нужна обёртка `async_to_sync(...)`, но это буквально шаблонный вызов в одну строку, не требующий освоения asyncio целиком.

## 9. Сценарий целиком: что меняется в `room_confirm_ready` и куда доходит

```
1. Игрок открывает room_detail.html.
   JS страницы: new WebSocket(".../ws/multiplayer/rooms/ABC123/")
   → см. §6 → RoomConsumer.connect() → вступление в группу "room_ABC123"

2. Другой игрок нажимает "Подтвердить готовность".
   Это ПО-ПРЕЖНЕМУ обычный Django view room_confirm_ready — обычный
   HTTP POST, ничего в самой логике не меняется.

3. В конце вьюхи (новый код, единственное дополнение):
       is_ready = True, room_player.save()                 # как сейчас
       html = render_to_string("multiplayer/_room_status.html", ...)
       async_to_sync(channel_layer.group_send)(
           f"room_{room.token}",
           {"type": "room.update", "html": html},
       )

4. Redis разносит это сообщение всем воркерам, у которых есть
   открытые сокеты в группе "room_ABC123" (см. §7).

5. У каждого такого соединения вызывается метод-обработчик
   RoomConsumer — Channels сам выводит имя метода из "type":
   "room.update" → room_update() (точка становится подчёркиванием).

   def room_update(self, event):
       self.send(text_data=event["html"])

6. Фронтенд получает HTML и подменяет DOM. Проще всего —
   расширение htmx-ws (https://htmx.org/extensions/ws/), которое
   умеет делать это декларативно, без своего JS, и хорошо
   ложится на то, что _room_status.html уже сейчас — самодостаточный
   фрагмент, используемый и для {% include %}, и для AJAX-подмены.
```

Важно: **вся текущая логика (`room_join`, `room_quit`, `room_set_quiz`, `room_confirm_ready`, будущий `room_start`) не переписывается**. Она как была обычными Django-вьюхами, так и остаётся. Добавляется один новый шаг в конце каждой — "оповести группу".

## 11. Деплой — решение принято: Daphne

Gunicorn (WSGI) в принципе не умеет отдавать WebSocket — это не вопрос настройки, а ограничение самого протокола WSGI (нет способа держать долгоживущее соединение и слать данные по инициативе сервера). Было два варианта:

- **Полностью перейти на Daphne** как основной сервер приложения — он одинаково хорошо отдаёт и обычный HTTP, и WebSocket. Меньше двигающихся частей.
- Либо держать оба: Gunicorn для обычного HTTP и отдельно Daphne только под `/ws/`-путь, а Nginx как reverse proxy разруливает по префиксу пути.

**Выбран первый вариант** (сессия от 2026-09-01, зафиксировано в `quiz_project_plan.md`, Этап 5) — на проде будет только Daphne, без Gunicorn вообще. Nginx перед ним остаётся как reverse proxy/статика/SSL-терминация, но проксирует уже на Daphne, с пробросом заголовков `Upgrade`/`Connection` для WS-пути. Redis на проде — обязательное условие для этого же этапа (не только под Celery, но и как Channel Layer, без него `group_send`/`group_add` работать не будут).

## 12. Локальная разработка: роль Daphne и Redis на Windows

**Daphne на деве — не то, что вы явно запускаете руками.** Когда `channels` попадает в `INSTALLED_APPS` и задан `ASGI_APPLICATION`, пакет **подменяет саму команду `manage.py runserver`** — снаружи всё выглядит как обычно (`python manage.py runserver`), но исполняет запросы уже Daphne под капотом, а не встроенный WSGI dev-сервер Django. Отдельно вызывать `daphne quiz_project.asgi:application` вручную понадобится только если вы захотите локально воспроизвести именно прод-подобный запуск (без auto-reload и прочих удобств `runserver`) — для повседневной разработки не нужно.

**Redis под Windows — через Docker Desktop (WSL2-бэкенд)**, выбранный вариант для этого проекта:

```
docker run -d --name redis -p 6379:6379 redis
```

Порт `6379` пробрасывается на `localhost` — Redis виден из нативно запущенного (не в контейнере) `runserver` как `localhost:6379`, ничем не отличаясь по факту от "Redis установлен локально". В `settings.py`:

```python
CHANNEL_LAYERS = {
    "default": {
        "BACKEND": "channels_redis.core.RedisChannelLayer",
        "CONFIG": {"hosts": [("localhost", 6379)]},
    },
}
```

Практические заметки:
- Без `-v` (volume) контейнер не сохраняет данные между перезапусками — для Channel Layer это не проблема, группы/подписки эфемерны по своей природе (в отличие от гипотетического использования того же Redis как кэша с данными, которые жалко терять).
- После первого `docker run` — `docker start redis` / `docker stop redis`, не нужно пересоздавать контейнер каждый раз.
- Отладка: `docker exec -it redis redis-cli`, дальше `SMEMBERS room_ABC123` покажет, какие имена-ящики реально состоят в группе — полезно, когда `group_send` вроде отработал, а клиент ничего не получил (проверить, действительно ли нужный `channel_name` попал в группу через `group_add`).

---

## 13. Рекомендация по объёму первой итерации

Заводить Channels стоит **только под лобби** (`multiplayer`), не трогая `gameplay` — там сейчас нет проблемы поллинга вообще (таймер вопроса — клиентский `setInterval`, без HTTP-запросов). Синхронизация текущего вопроса в мультиплеерном `gameplay` (когда дойдёт очередь до общего `GameSession.current_question`) может либо позже тоже переехать на тот же Channel Layer, либо первое время остаться на редком поллинге — это не то же узкое место, что 2-секундный поллинг лобби.
