# CLAUDE.md

## Режим работы с пользователем

**Важно: пользователь пишет этот проект сам.** Claude в этом репозитории выступает в роли технического консультанта/senior-инженера, к которому обращаются за советом — не как исполнитель, который сам пишет код и делает коммиты.

- По умолчанию **не пиши код и не редактируй файлы**, пока пользователь явно не попросит внести конкретное изменение.
- На вопросы вида "как лучше сделать X", "куда это положить", "правильно ли я делаю Y" — отвечай как консультация: рекомендация + обоснование + альтернативы/trade-off'ы, без немедленной реализации.
- Если пользователь просит именно написать/поправить код — это исключение из общего режима, делай это как обычно.
- Не бери на себя архитектурные решения самостоятельно — предлагай варианты, финальный выбор за пользователем.

## О проекте

**QuizApp** — платформа для создания и прохождения викторин с AI-генерацией вопросов (Claude API), соло и мультиплеер-режимами, соцфункциями (подписки, лайки, челленджи) и монетизацией.

Полный план — в [`quiz_project_plan.md`](quiz_project_plan.md): стек, структура папок, модели, сценарии использования, этапы разработки.

### Стек
Django 5 (sync) + PostgreSQL + Redis + Celery + Django Channels (WebSocket) + HTMX + Anthropic Claude API. Деплой — Hetzner/DigitalOcean (Frankfurt), Gunicorn + Nginx.

### Ключевое архитектурное правило
Приложение `ai_generator` зависит от `quizzes` (импортирует его модели, чтобы сохранять сгенерированные викторины), но не наоборот. `quizzes` — чистое хранилище/отображение (`Quiz`, `Question`, `AnswerOption`), не знает, создана ли викторина вручную или через AI. Форма параметров AI-генерации (тема, кол-во вопросов, сложность, стиль) размещается в `ai_generator`, а не в `quizzes`. Подробности — в разделе "Правило взаимодействия quizzes ↔ ai_generator" в плане.

- По ходу той же сессии разобран сам механизм `question_formset.management_form`/`TOTAL_FORMS` по исходникам Django (`django/forms/formsets.py`, `BaseFormSet`): `total_form_count()` для bound-формсета возвращает значение `TOTAL_FORMS` из `request.POST` (с потолком `absolute_max` — защита от DoS, если кто-то пришлёт заведомо большое число), `forms` (`cached_property`) строит список подформ циклом `range(total_form_count())`, каждая подформа получает `prefix=f"{formset.prefix}-{i}"` и сама выбирает свои поля из общего `request.POST`. `INITIAL_FORMS` — отдельная величина, определяющая, какие индексы формсет считает формами "существующих" объектов (`i < INITIAL_FORMS`, `save_existing_objects()`) против "новых" (`i >= INITIAL_FORMS`, `save_new_objects()`, `empty_permitted=True`, пустые/непомеченные формы пропускаются); в `QuizzesCreateView` формсет всегда создаётся без готового `queryset`, поэтому `INITIAL_FORMS=0` и все формы идут по ветке "новый объект". #### Часть 1 — CSRF `Forbidden (CSRF token missing.)` на `room_confirm_ready`, нестабильно у `cat`

Симптом: у `cat` иногда (не всегда) 403 при клике «Подтвердить готовность», и после этой ошибки WS-обновления лобби переставали приходить до ручной перезагрузки страницы.

**Диагноз**: `multiplayer/consumers.py::room_update()` вызывал `render_to_string("multiplayer/_room_status.html", context)` **без `request=`** — `{% csrf_token %}` берёт значение из `context['csrf_token']`, которое туда кладёт либо `RequestContext`, либо явный `get_token(request)`; без `request` тег молча рендерит пустую строку (не невалидный токен — поля вообще нет в HTML). Форма подтверждения готовности жила внутри `_room_status.html`, то есть каждый раз, когда WS-пуш (от **любого** действия в комнате — join/set-quiz/ready другого игрока) подменял `#room-status` через `outerHTML`, CSRF-поле формы исчезало. Пока пользователь ещё не получил ни одного WS-пуша с момента обычного `GET` (с валидным, отрендеренным через реальный `request` токеном) — форма рабочая; после первого пуша — 403 «token missing». Отдельно объяснено, почему после этого гаснет WS: страница CSRF-failure — полноценный отдельный HTML-документ, обычный `<form method="post">` — это full page navigation, а не `fetch`; браузер уходит со страницы, вместе с DOM уничтожается и открытый `WebSocket`/`onmessage`, только ручной возврат на `room_detail.html` открывает новый сокет с новым валидным токеном.

**Первая версия фикса — `fetch()` + заголовок `X-CSRFToken`** (Claude реализовал по прямой просьбе): читать `csrftoken` из cookie на клиенте, слать `POST` через `fetch` с заголовком вместо обычного `<form>`-сабмита — стандартный Django-паттерн для форм, вставляемых в DOM без `request`-контекста. Работало, но пользователь указал на побочный эффект — раз это `fetch`, а не навигация браузера, `redirect(...)` в конце `room_confirm_ready` больше не превращается в переход страницы (браузер под капотом следует за `302`, но ответ никуда не читается), а `messages.success(request, "Готовность подтверждена")` оседает в сессии и никогда не отображается. Объяснено пользователю: это не следствие способа передачи токена (заголовок vs скрытое поле), а следствие перехода на `fetch` вообще — обычная HTML-форма физически не может слать кастомные заголовки, только `fetch`/`XHR` умеют.

**Финальное решение (по выбору пользователя) — вернуться к обычному `<form method="post">`, убрать причину пустого токена, а не подстраиваться под неё**:
- `_room_status.html` — форма/сообщение готовности убраны совсем, остался только read-only список (название квиза + участники) — то, что безопасно перерендеривать без `request`.
- `room_detail.html` — форма `#confirm-ready-form` (с реальным `{% csrf_token %}`) и `<p id="ready-confirmed-msg">` вынесены наружу, рендерятся **один раз** через обычный `GET` (валидный токен на весь «сеанс» страницы), видимость сразу вычисляется на сервере (`hidden`, если `not object.current_quiz or my_room_player.is_ready` — соответственно для формы, и наоборот для сообщения).
- `multiplayer/consumers.py::room_update()` — вместо готового HTML для этой части шлёт JSON `{"html": ..., "can_confirm": bool, "is_ready": bool}`; JS в `room_detail.html` подменяет `#room-status` как раньше, а `#confirm-ready-form`/`#ready-confirmed-msg` просто переключает через `.hidden`, не пересоздавая — тот самый (уже существующий на форме) `<form>` с валидным токеном никогда не перерендеривается без `request`.
- Итог: обычный `POST`+`redirect`+`messages` работает как везде в проекте (`room_join`/`room_quit`/`room_set_quiz`), никакого `fetch`, никакой AJAX-специфики.

Исправлено — `_check_and_make_complete` при завершении мультиплеерной сессии дополнительно возвращает `sess.room.status = "waiting"` (если `sess.room_id` есть — теперь есть, см. пункт выше). `current_game_session` осознанно не зануляется — условие редиректа требует **оба** поля (`status == "in_progress"` и `current_game_session_id`), достаточно снять первое; `current_game_session` продолжает быть полезен для истории/ссылки на комнату.
- **Итог сессии, проверено пользователем в браузере**: полный цикл — создание комнаты → приглашение → выбор квиза → готовность → «Начать» → игра с общим текущим вопросом на всех участников → завершение → результат с рабочей ссылкой «Вернуться в комнату» → повторный раунд в той же комнате (квиз можно сбросить/выбрать заново, не попадая в старую игру) — работает без 500 и без ложных редиректов.

Планируется WS по аналогии с уже обкатанным на лобби `RoomConsumer` — вероятно отдельная группа на сессию (`session_<id>`), а не переиспользование `room_<token>` (см. открытый пункт в сессии от 2026-09-02). #### Часть 1 — `GameSessionConsumer`: от каркаса до рабочего WS, ~10 последовательных багов

Симметрично `RoomConsumer` заведены `gameplay/routing.py` (`ws/gameplay/session/<pk>/` → `GameSessionConsumer`) и `gameplay/consumers.py`; `quiz_project/asgi.py` объединяет маршруты обоих приложений в один `URLRouter` (`multiplayer.routing.websocket_urlpatterns + gameplay.routing.websocket_urlpatterns`). Хронология находок ревью (каждая всплывала только после исправления предыдущей — типичная цепочка при разработке нового фрагмента по частям):

1. **`asgi.py` не импортировал `gameplay.routing` вообще** — IDE подчёркивала `gameplay` как неизвестное имя; добавлен `import gameplay.routing` после `django_asgi_app = get_asgi_application()` (тот же порядок, что и для `multiplayer.routing`, — иначе `AppRegistryNotReady`).
2. **`gameplay/consumers.py` изначально был копипастой `multiplayer/consumers.py`** — `from .models import Room` (в `gameplay.models` нет `Room`, она в `multiplayer.models`) и `from .views import _get_room_context` (тоже только в `multiplayer`), при пустом теле `GameSessionConsumer(pass)`. Упало бы `ImportError` при первом же импорте `gameplay.routing`. Пользователь переписал класс с нуля по аналогии с `RoomConsumer` (группа `session_<id>`, `connect()` проверяет участие через `GameParticipant`).
3. **`play.html` — WS вообще не подключался**: `new WebSocket(... + "ws/gameplay/session/{{ session.pk }}/")` — не было `session` в контексте (только `current_session`, resolves в пустую строку) и не было ведущего `/` перед `ws/gameplay/...`. Исправлено на `"/ws/gameplay/session/" + "{{ current_session.pk }}" + "/"`.
4. **`_players_status.html` — сравнение `{% if answer == current_answer %}`** сравнивало ответ каждого участника не с текущим вопросом сессии, а с объектом `current_answer` смотрящего пользователя — Django сравнивает модели по `pk`, так что условие истинно только для **своего же** ответа; через WS (`current_answer` в контексте `session_update` не было вовсе) список был всегда пуст. Исправлено на `answer.question_id == current_session.current_question_id`.
5. **`_notify_session` изначально стрелял только когда раунд полностью продвигался** (из `_check_and_advance_round`), не на каждый отдельный ответ — добавлен вызов и в `_update_gameAnswer`, чтобы статус «кто уже ответил» обновлялся у всех сразу после каждого сабмита, а не только когда раунд целиком сдвигается.
6. **`play.html:52` — `outerHTML`-свап ломался после первого же сообщения**: `_players_status.html` рендерился с корневым `id="players-status"`, а свап целился в `#waiting-info` — после первой замены `id="waiting-info"` пропадал из DOM, следующее сообщение падало на `null.outerHTML`. Тот же класс ошибки, что уже решён для `_room_status.html` (сессия от 2026-08-30) — обёртка должна быть **внутри** партиала. Исправлено переносом `id="waiting-info"` на корень `_players_status.html`, `play.html` больше не оборачивает партиал отдельным `<div>`.
7. **После фикса №6 видимость блока перестала работать корректно** (двумя заходами): сначала `waitingInfo.hidden = !data.already_answered` после `outerHTML`-свапа ставилось на уже отсоединённый (протухший) узел — тот же класс бага, что и №6, просто для `.hidden`, а не для поиска элемента; затем, когда убрали эту строку и сделали `hidden` статичным атрибутом шаблона, видимость перестала обновляться уже в обратную сторону (всегда скрыт). Финальное решение — `already_answered` прокидывается в контекст `render_to_string` внутри `session_update()` (`consumers.py`) точно так же, как уже передаётся в контекст `_play_multiplayer`, и `_players_status.html:1` рендерит `hidden` условно: `<div id="waiting-info"{% if not already_answered %} hidden{% endif %}>` — видимость целиком «печётся» в HTML, который приходит с сервера, JS больше не трогает `.hidden` вообще (только одна строка `outerHTML =` в `onmessage`).
8. **`_players_status.html` — забытый `{% endif %}`** (внешний `{% if answer.question_id == ... %}` со строки 6 не был закрыт, только вложенный `{% if answered_at or is_skipped %}` со своим `endif`) — `TemplateSyntaxError: Invalid block tag 'endfor', expected ... 'endif'`. Добавлен недостающий `{% endif %}`.
9. **`session_update()` падал `GameAnswer.DoesNotExist`, когда `session.current_question` временно становится `None`** (окно между тем, как `_check_and_advance_round` продвигает раунд до конца вопросов, и тем, как следующий `GET` через `_check_and_make_complete` переводит `status` в `completed`) — `question` у `GameAnswer` не бывает `NULL`, `.get(question=None)` гарантированно падал у каждого ожидающего на последнем вопросе любой партии. Исправлено — `already_answered` считается только если `session.current_question is not None`, иначе остаётся `False`.
10. **`participant = session.participants.filter(user=user)`** передавался как queryset напрямую в следующий `.get(participant=participant, ...)` вместо единичного объекта — исправлено на паттерн `next((p for p in session.participants.all() if p.user_id == user.id), None)`, тот же, что уже используется в `views.py::play()`/`result()` (заодно читает из уже прогретого `prefetch_related`, а не бьёт в БД заново, как било бы `.filter()` на related-менеджере).
11. **`session.participants.participants_answers.all()`** — `AttributeError`, `participants_answers` это related_name у `GameAnswer`, доступный только на конкретном `GameParticipant`, не на менеджере списка участников. Исправлено на `participant.participants_answers.all()` (использует тот же прогретый кэш, что и находка №10) + сравнение поправлено на `a.question_id == session.current_question_id` (было сравнение `id` с объектом `Question`, всегда `False`).

**Главная оставшаяся задача цикла — как отличить «кто-то ещё ответил на этот же вопрос» от «раунд продвинулся, нужно показать новый вопрос»** — обе ветки шлют один и тот же сигнал `{"type": "session.update"}`, а `views.py` менять не хотелось (решение по аналогии с `RoomConsumer.room_update()`, который сам смотрит на стабильный предикат `room.status`/`current_game_session_id`, а не полагается на разные типы события из `views.py`). Решено консьюмер-side: `connect()` запоминает `self.last_question_id = session.current_question_id`; каждый `session_update()` сравнивает актуальное значение с запомненным — если отличается (раунд продвинулся или сессия завершилась, `current_question` стал `None`), консьюмер обновляет `self.last_question_id` **до** отправки (иначе повторный `session_update`, долетевший до того же ещё не разорванного соединения раньше, чем браузер успеет обработать первый редирект и уйти со страницы — а `_notify_session` для одного продвижения раунда стреляет дважды: из `_update_gameAnswer` и из `_check_and_advance_round` — заново увидел бы «отличается» и отправил бы лишний, хоть и безвредный, повторный редирект) и шлёт `{"type": "redirect", "url": .../play/}"` — полная перезагрузка страницы, а не частичный свап (`_play_multiplayer` на свежем `GET` сам разберётся, показывать новый вопрос или редиректить дальше на `result/`, если к этому моменту `status` уже `completed`). Если вопрос тот же — как обычно, партиал `_players_status.html`. При реальной перезагрузке (F5 или переход по этому же редиректу) создаётся полностью новый экземпляр `Consumer` — `self.last_question_id` пересчитывается в `connect()` с нуля, никакого протухшего состояния между разными TCP-соединениями быть не может (тот же принцип уже разбирался для `RoomConsumer` при обсуждении переподключений лобби).

#### Часть 2 — `transaction.on_commit` для всех `_notify_session`/`_notify_room`

По ходу разбора находки №9 выше всплыл более общий вопрос: `_notify_session`/`_notify_room` вызываются **внутри** `with transaction.atomic()`, до её коммита — WS-консьюмер читает БД через отдельное соединение и в теории может успеть выполнить свой запрос быстрее, чем текущая транзакция закоммитится, увидев устаревшее состояние (тот же класс проблемы уже обсуждался как трейд-офф для `_notify_room` в сессии от 2026-09-03, там сознательно не стали чинить; здесь конкретно всплыло как вероятная причина, почему round-advance-детектор из Части 1 иногда мог бы не сработать). По прямой просьбе пользователя все вызовы обёрнуты в `transaction.on_commit(lambda: ...)`, с объясняющим комментарием на каждом месте (тоже по прямой просьбе — не молчаливый рефакторинг):
- `gameplay/views.py`: `_update_gameAnswer`, `_check_and_advance_round`, `_check_and_make_complete` (3 места)
- `multiplayer/views.py`: `room_join`, `RoomPlayerDeleteView.form_valid`, `room_set_quiz`, `room_reset_quiz`, `room_confirm_ready`, `room_start` (6 мест)

`transaction.on_commit()` всегда откладывает колбэк до коммита самой внешней транзакции, даже если вызван из вложенного `with transaction.atomic()` (тот вложенный блок — просто savepoint, не отдельная транзакция) — это и разбиралось отдельно с пользователем перед реализацией (конкретно вопрос "будет ли переиспользован старый `self.last_question_id` при новом WS-соединении после редиректа" — нет, не будет, разобрано в Части 1).

#### Часть 4 — откаченный эксперимент: задержка перед следующим вопросом с показом `Question.fact`

Пользователь заметил, что блок «Любопытный факт» (`#fact`, давно существующее поле `Question.fact`) виден только ожидающим в мультиплеере (`already_answered && mode === "multiplayer"`), а в соло не виден никогда — сервер редиректит на следующий вопрос сразу после сабмита, факт физически не успевает отрендериться. Обсуждался и был реализован (по прямой просьбе, вместе — сначала консультация с готовым сравнением вариантов, затем реализация пользователем, затем ревью Claude по шагам) клиентский вариант: перехват `submit` (`e.preventDefault()`), отправка через `fetch()` (тело — `new FormData(form)`, включая `csrfmiddlewaretoken`, который `{% csrf_token %}` рендерит по-настоящему валидным ещё на обычном `GET`), показ `#fact` сразу, переход на `response.url` (адрес уже после того, как `fetch` сам прошёл через 302-редирект `views.py::play()`) только через `setTimeout(..., FACT_DELAY_MS)`; флаг `navigating`, гасящий собственные WS-редиректы на время паузы, чтобы раунд, продвинутый твоим же ответом, не обрывал показ факта раньше времени.

**Пользователь счёл результат «страшным рассинхроном»** и откатил вручную (сначала — закомментировав JS через легаси-синтаксис `<!-- -->` внутри `<script>`, который действительно работает как построчный комментарий в браузерных движках, но крайне нестандартен; по просьбе пользователя Claude физически удалил закомментированный блок и связанные с ним неиспользуемые объявления `FACT_DELAY_MS`/`navigating`, вернув `play.html` ровно к состоянию до эксперимента). **Проверка в БД** (по просьбе пользователя, `GameSession pk=16`, 3 участника, 8 вопросов) показала: у **всех** участников по **всем** вопросам `GameAnswer.chosen_option is None`, `is_skipped=True`, `score=0` у всех троих — сервер ни разу не увидел выбранный вариант ответа за всю партию. Точная причина не установлена (баг ли самого fetch-подхода, или тестовый прогон был без реальных кликов по вариантам, только наблюдение за механикой задержки) — зафиксировано в `TODO.md` («Найдено при сессии от 2026-09-04») вместе с тремя возможными направлениями решения на будущее (доработка того же fetch-подхода с логированием `request.POST`; промежуточный «review»-экран через обычный `GET`/`POST`-цикл без `fetch` вообще; серверный `next_url` в контексте + чистый `setTimeout`/`meta refresh` без WS-флагов). **`_update_total_score`/`_update_gameAnswer` при этом отдельно перепроверены и признаны корректными** — 0 очков объясняется отсутствием `chosen_option`, а не багом в подсчёте.
