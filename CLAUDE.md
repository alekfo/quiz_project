# CLAUDE.md

## Режим работы с пользователем

**Важно: пользователь пишет этот проект сам.** Claude в этом репозитории выступает в роли технического консультанта/senior-инженера, к которому обращаются за советом — не как исполнитель, который сам пишет код и делает коммиты.

- По умолчанию **не пиши код и не редактируй файлы**, пока пользователь явно не попросит внести конкретное изменение.
- На вопросы вида "как лучше сделать X", "куда это положить", "правильно ли я делаю Y" — отвечай как консультация: рекомендация + обоснование + альтернативы/trade-off'ы, без немедленной реализации.
- Если пользователь просит именно написать/поправить код — это исключение из общего режима, делай это как обычно.
- Не бери на себя архитектурные решения самостоятельно — предлагай варианты, финальный выбор за пользователем.

## О проекте

**QuizApp** — платформа для создания и прохождения викторин с AI-генерацией вопросов (Claude API), соло и мультиплеер-режимами, соцфункциями (подписки, лайки, челленджи) и монетизацией.

Полный план — в [`quiz_project_plan.md`](quiz_project_plan.md): стек, структура папок, модели, сценарии использования, этапы разработки.

### Стек
Django 5 (sync) + PostgreSQL + Redis + Celery + Django Channels (WebSocket) + HTMX + Anthropic Claude API. Деплой — Hetzner/DigitalOcean (Frankfurt), Gunicorn + Nginx.

### Ключевое архитектурное правило
Приложение `ai_generator` зависит от `quizzes` (импортирует его модели, чтобы сохранять сгенерированные викторины), но не наоборот. `quizzes` — чистое хранилище/отображение (`Quiz`, `Question`, `AnswerOption`), не знает, создана ли викторина вручную или через AI. Форма параметров AI-генерации (тема, кол-во вопросов, сложность, стиль) размещается в `ai_generator`, а не в `quizzes`. Подробности — в разделе "Правило взаимодействия quizzes ↔ ai_generator" в плане.

- По ходу той же сессии разобран сам механизм `question_formset.management_form`/`TOTAL_FORMS` по исходникам Django (`django/forms/formsets.py`, `BaseFormSet`): `total_form_count()` для bound-формсета возвращает значение `TOTAL_FORMS` из `request.POST` (с потолком `absolute_max` — защита от DoS, если кто-то пришлёт заведомо большое число), `forms` (`cached_property`) строит список подформ циклом `range(total_form_count())`, каждая подформа получает `prefix=f"{formset.prefix}-{i}"` и сама выбирает свои поля из общего `request.POST`. `INITIAL_FORMS` — отдельная величина, определяющая, какие индексы формсет считает формами "существующих" объектов (`i < INITIAL_FORMS`, `save_existing_objects()`) против "новых" (`i >= INITIAL_FORMS`, `save_new_objects()`, `empty_permitted=True`, пустые/непомеченные формы пропускаются); в `QuizzesCreateView` формсет всегда создаётся без готового `queryset`, поэтому `INITIAL_FORMS=0` и все формы идут по ветке "новый объект". Сознательно не обёрнуты в try/except остальные операции с БД в `quizzes`/`ai_generator` (создание `Quiz`/`Question`/`AnswerOption`) — там ожидаемых сценариев отказа нет, пусть падают в 500 и логируются штатно через `django.request` (уже настроен на `console`).
- **Формсет-валидация вопросов**: `quizzes/forms.py` → `BaseQuestionFormSet(forms.BaseInlineFormSet)`, подключён в `QuestionFormSet` через `formset=BaseQuestionFormSet` (`inlineformset_factory`). В `clean()` — после стандартного guard'а `if any(self.errors): return` (не наслаивать формсетные ошибки поверх уже существующих ошибок отдельных форм) считает `active_forms` (`has_changed()` и не помечена `DELETE` — то же условие, по которому реально определяются сохраняемые вопросы в `QuizCreateView.forms_valid`) и проверяет два инварианта: минимум 2 активных вопроса, уникальность `order` среди них. Ошибки уходят в `question_formset.non_form_errors()`, отрендерены в `quiz_form.html` (`<div class="formset_errors">{{ question_formset.non_form_errors }}</div>`) — до этой сессии рендера не было, такие ошибки были бы невидимы пользователю.
- **Flash-сообщения через `django.contrib.messages`**: `{% if messages %}` блок добавлен в `quizzes/base.html` и `ai_generator/base.html` (по образцу уже существовавшего в `users/base.html`). `messages.error(...)` — в `QuizCreateView.forms_invalid` (общий баннер поверх точечных ошибок формы/формсета) и в `ai_generator/views.py::index()` при сбое Claude. `messages.success(...)` — в новом `QuizDeleteView.get_success_url()`. `quizzes/base.html` дополнительно получил JS: `setTimeout` на 15 секунд, который через `document.querySelector('.messages')` + `Element.remove()` убирает блок сообщений из DOM (не просто прячет через CSS) — таймер живёт только в рамках текущей загрузки страницы. **В `ai_generator/base.html` этого JS нет** — стоит сверить, нужен ли он там тоже, при следующей сессии.
- **Новый `QuizDeleteView`** (`quizzes/views.py` + `quizzes/urls.py` → `<int:pk>/delete/`, `name='quizzes_delete'`). Логирование (`logger.info`, читает `self.object.pk`) и `messages.success(...)` вынесены именно в `get_success_url()`, а не в переопределённый `delete()` — не произвольный выбор: `DeletionMixin.delete()` (`django/views/generic/edit.py`) вызывает `get_success_url()` **до** `self.object.delete()`, а `Model.delete()`/`Collector.delete()` после реального удаления зануляет `self.object.pk` на инстансе — значит залогировать pk удаляемого объекта можно только на этом шаге. Побочный эффект (не исправлено, не критично сейчас): лог/сообщение технически говорят "успешно удалено" чуть раньше, чем `self.object.delete()` реально отработал; для `Quiz` это не проблема, т.к. `Question.quiz` на `CASCADE` и ничего не блокирует удаление через `PROTECT`.
- Первая версия `QuizDeleteView.success_url` была задана как **атрибут класса** (`success_url = reverse("quizzes:quizzes_list")`) — падало `ImproperlyConfigured: ... does not appear to have any patterns ... probably caused by a circular import`, потому что `reverse()` в теле класса выполняется в момент импорта `quizzes/views.py`, а этот импорт сам является частью ещё не достроенного дерева `urlconf` (`quiz_project/urls.py` → `include('quizzes.urls')` → `quizzes/views.py`). Исправлено переносом построения URL в `get_success_url()` (обычный метод, выполняется при обработке запроса, когда urlconf уже полностью загружен) — что заодно совпало с необходимостью логировать `pk` до удаления (см. выше). Хвост: `reverse_lazy` по-прежнему импортирован в `quizzes/views.py`, но нигде не используется — мёртвый импорт.
- Классы во `views.py` переименованы с `Quizzes*` на `Quiz*` (`QuizDetailView`, `QuizListView`, `QuizCreateView` — было `QuizzesDetailView` и т.д.); имена url-паттернов (`quizzes_details`, `quizzes_list`, `quizzes_create`, `menu`) не менялись, только имена классов.
- **Появился первый CSS-файл проекта**: `static/css/main.css`, подключён в `quizzes/base.html` (`{% load static %}` + `<link rel="stylesheet" href="{% static 'css/main.css' %}">`; забытый `{% load static %}` сначала ронял рендер `TemplateSyntaxError: Invalid block tag 'static'`, добавлен). Стилизует `.messages li.error`/`.messages li.success` (по классу из `message.tags`, который Django сам подставляет по уровню сообщения), `.formset_errors`, `.delete_link`. **В `ai_generator/base.html` `{% load static %}`/`<link>` пока не добавлены** — стили туда не подключены, стоит сверить при следующей сессии заодно с JS-блоком выше.
