# План изменений бэкенда

Пользователь пишет бэкенд сам и использует план, чтобы не держать проект в памяти.
Соблюдай распределение ролей и разрешения AGENTS.md.

## Подготовка

Прочитай актуальные инструкции, git status/diff и относящиеся к задаче модели,
вьюхи, сервисы, URL, потребителей контекста и тесты. Старый план и документация
не заменяют чтение кода. Сам выясни, что уже реализовано и что требуется фронтенду.
Обсуждай только действительно неоднозначные решения пользователя, а не вопросы,
на которые можно ответить чтением проекта. Предложения не выдавай за согласования.

## Файл плана

В названном пользователем файле оставляй только невыполненные изменения
бэкенда, которые должен сделать пользователь. Каждый пункт содержит:

- точный файл и функцию/класс;
- установленную текущую проблему или недостающие данные;
- что конкретно добавить, заменить, перенести или удалить;
- ожидаемый результат; для контекста — ключи и структуру данных.

Располагай небольшие шаги по зависимостям. Предлагай точечные изменения,
без переписывания целых файлов. Код решения давай только по просьбе.

Не включай уже сделанное, «сохранить существующее», историю обсуждения,
отвергнутые альтернативы, общие чек-листы и гипотетическое расширение задачи.
Не поручай пользователю «проверить все места»: выполни аудит сам и сформулируй
найденную необходимую правку. Тесты, фронтенд и браузерную проверку Codex
не смешивай с пользовательским списком. Если запрошен общий план команды,
вынеси задачи Codex в явно отдельный раздел или документ.

Каждое указание сверяй с существующим кодом, включая вызываемые helper-функции.
Если проверка доступа или другое требование уже реализовано, отдельного шага
не добавляй. Различай право просмотра, отправки ответа и управления игрой;
не предлагай проверять создателя общей multiplayer-сессии вместо участия игрока.
Вместо «проверить права» укажи конкретное недостающее условие и место его
выполнения. Объяснения существующей механики давай в чате по необходимости,
а не превращай их в задачи пользователя.

Для конкурентных изменений проследи весь путь до фактических UPDATE, включая
helper-функции: единый порядок явных select_for_update не исключает обратного
порядка блокировок при save(). Не описывай защиту от гонки как готовую, пока
смежные пути завершения и запуска используют несовместимый порядок блокировок.

Пример пункта:

> `gameplay/views.py`, `start`: поиск активного прогона не ограничен mode.
> При mode=multiplayer вывести сообщение и вернуть на превью; в solo_room
> направлять только соло-прогон. Сейчас ведущий попадает в другой режим.

## После изменений пользователя

1. Прочитай свежий дифф и смежные пути выполнения. Для ревью этого проекта
   примени .agents/skills/pitfalls-check/SKILL.md.
2. Сам запусти проверки по AGENTS.md. Различай баг и устаревшее ожидание теста.
   Неполный или зависший прогон не выдавай за полный. Бэкенд сам не исправляй.
3. В чате коротко сообщи выполненное, реальные ошибки и результаты проверок.
4. Удали выполненные пункты из плана, не оставляй их с галочками. Обнови остаток
   по текущему коду. Если бэкенд готов — скажи об этом, не выдумывай новые задачи.

Если пользователь просит замечания только в чате/терминале и запрещает новый
план, дай точечные исправления там; файл плана в этом случае не переписывай.

## Цикл работы

Обсуждение → .md-план конкретных правок пользователю → бэкенд пользователя
→ ревью Codex и сокращение остатка → тесты Codex по разрешению пользователя
→ фронтенд Codex после согласования компонента → браузерная проверка.

Ошибки бэкенда закрываются до фронтенда. План не даёт автоматического разрешения
править код. В новой сессии читай текущий план и код, не начинай прежний список заново.
