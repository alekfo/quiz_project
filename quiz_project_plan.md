## Стек технологий

| Компонент | Технология |
|---|---|
| Бэкенд | Django 5.x (синхронный) |
| База данных | PostgreSQL |
| Кэш / брокер | Redis |
| Фоновые задачи | Celery |

## Основные модели

### users/
- **Profile** — аватар, bio, рейтинг, количество викторин, подписчики

### quizzes/
- **Category** — название темы (история, наука, спорт, кино...)
- **Quiz** — название, описание, автор, тип (AI / ручная), категория, публичная/приватная, лайки, теги, `time_limit_seconds` (лимит времени на вопрос в секундах, задаётся автором при создании квиза, единый для всех вопросов — решение зафиксировано в разделе «Соло прохождение»: игрок это значение не выбирает, чтобы в будущем мультиплеере у всех участников партии было одинаковое время)
- **Question** — текст вопроса, таймер, изображение (опционально), интересный факт (генерируется AI вместе с вопросом — отклонение от исходного плана: изначально это поле числилось за `AnswerOption` как «объяснение ответа», но Claude возвращает факт на уровне вопроса целиком, а не привязанным к конкретному варианту ответа, поэтому поле перенесено на `Question`)
- **AnswerOption** — варианты ответа, какой правильный

### ai_generator/
- **GenerationRequest** — параметры (тема, кол-во вопросов, категория, сложность, стиль), статус задачи, результат

### gameplay/
- **GameSession** — викторина (FK `Quiz`), режим (`solo` / `multiplayer`, задел на Этап 3 — мультиплеер), статус (`in_progress` / `completed` / `abandoned`, default `in_progress`), `started_at` (auto_now_add), `finished_at` (nullable, проставляется когда участник отвечает на последний вопрос)
- **GameParticipant** — сессия (FK `GameSession`, `related_name="participants"`), пользователь (FK `User`), `score` (default 0), `joined_at` (auto_now_add). `unique_together (game_session, user)`. Для соло-режима на сессию всегда ровно один участник — модель вынесена отдельно от `GameSession`, чтобы позже под мультиплеер не переделывать FK на User в M2M на живых данных (см. обсуждение архитектуры)
- **GameAnswer** — участник (FK `GameParticipant`, `related_name="answers"`), вопрос (FK `Question`), выбранный вариант (FK `AnswerOption`, nullable — пусто при таймауте/пропуске), `is_correct` (bool), `is_skipped` (bool, default `False`), `shown_at` (DateTimeField, момент показа вопроса — точка отсчёта для серверной проверки таймера), `answered_at` (DateTimeField, nullable, момент фактического ответа). `unique_together (participant, question)`. Строка создаётся уже в момент **показа** вопроса (не только при ответе) и служит единственным источником истины о прогрессе — см. «Соло прохождение» ниже, отдельного поля-указателя "текущий вопрос" на `GameSession` нет

### multiplayer/
- **Room** — код комнаты, хост, статус (ожидание / игра / завершена), викторина
- **RoomPlayer** — участник комнаты, текущий счёт в реальном времени

### social/
- **Follow** — подписки между пользователями
- **QuizLike** — лайки на викторины
- **Invite** — приглашение в комнату по ссылке

## Правило взаимодействия quizzes ↔ ai_generator

Направление зависимости — только одностороннее: **ai_generator зависит от quizzes, но не наоборот.**

- **quizzes** — «хранилище» сущностей викторины (`Quiz`, `Question`, `AnswerOption`). Ничего не знает о том, как викторина была создана — вручную или через AI. Отвечает только за хранение, отображение, каталог, прохождение.
- **ai_generator** — весь процесс AI-генерации целиком:
  - форма с параметрами запроса (тема, кол-во вопросов, сложность, стиль) — размещается **здесь**, а не в quizzes;
  - модель `GenerationRequest` (статус задачи, параметры, результат);
  - Celery-задача, запрос к Claude API, промпты (`prompts.py`);
  - парсинг JSON-ответа и запись результата в модели quizzes (`ai_generator` импортирует `Quiz`/`Question`/`AnswerOption`, создаёт объекты).

Смысл разделения: AI-функциональность можно отключить/заменить, не трогая ядро (quizzes). Ручное создание викторины (Этап 2) — это форма и view в самом quizzes, поскольку не требует Celery/внешнего API.

## Сценарии использования

### AI-генерация викторины
```
Пользователь заполняет форму (тема, кол-во, сложность, стиль)
    → Django создаёт GenerationRequest в БД
    → Celery задача уходит в очередь
    → HTMX polling каждые 2 сек проверяет статус
    → Celery делает запрос к Claude API
    → Claude возвращает JSON с вопросами
    → Вопросы сохраняются в Quiz/Question
    → Пользователь видит готовую викторину
    → Публикует или оставляет приватной
```

### Ручное создание викторины
```
Форма создания викторины (название, категория, описание)
    → Добавление вопросов по одному
    → Превью викторины
    → Публикация
```

### Соло прохождение

Общий флоу:
```
Пользователь выбирает викторину из списка (свои + публичные)
    → POST на старт → создаётся GameSession (mode=solo, status=in_progress) + GameParticipant
    → redirect на экран прохождения
    → GET экрана прохождения вычисляет текущий вопрос:
        первый Question квиза (по order), для которого у участника
        ещё нет GameAnswer с answered_at != null ИЛИ is_skipped = True
        → если такого вопроса не осталось — redirect на итоговый экран
        → если есть — get_or_create GameAnswer(participant, question, defaults={shown_at: now()})
          (get_or_create — принципиально: если пользователь обновит страницу,
          shown_at не должен сброситься, иначе таймер обнуляется бесплатно)
          → рендер вопроса + клиентский JS-таймер на quiz.time_limit_seconds
    → пользователь выбирает вариант ответа, либо истекает клиентский таймер (авто-сабмит пустой формы)
    → POST ответа на этот же вопрос
        → сервер находит GameAnswer(participant, question); если answered_at уже проставлен — просто
          redirect дальше (защита от повторного сабмита формы, например через "назад" в браузере)
        → сверяет now() - shown_at с quiz.time_limit_seconds — если просрочено, ответ форсится как
          is_skipped=True вне зависимости от того, что реально пришло в теле запроса
        → иначе сохраняет selected_option, is_correct, answered_at = now()
        → обновляет GameParticipant.score, если ответ верный
        → redirect обратно на экран прохождения — цикл повторяется для следующего вопроса
    → когда неотвеченных/непропущенных вопросов не осталось:
        GameSession.status = completed, finished_at = now()
        → redirect на итоговый экран
    → итоговый экран: score, время прохождения, разбор по каждому GameAnswer
      (вопрос / выбор игрока / правильный вариант / факт из Question.fact)
```

#### Координация по вопросам: URL-схема

Явного номера вопроса в URL нет — сервер всегда сам решает, какой вопрос показывать, исходя из истории `GameAnswer` участника (см. флоу выше). Если положить номер вопроса в URL (`/question/3/`), пользователь сможет вручную подкрутить его в адресной строке и перепрыгнуть вопрос или вернуться к уже отвеченному — состояние тогда пришлось бы валидировать отдельно, что просто дублирует ту же проверку, которую и так обязан делать сервер.

| Метод | URL | Что делает |
|---|---|---|
| `POST` | `/gameplay/quiz/<quiz_id>/start/` | Создаёт `GameSession` + `GameParticipant`, redirect на `play/` |
| `GET` | `/gameplay/session/<session_id>/play/` | Вычисляет и показывает текущий (первый неотвеченный) вопрос; если вопросов не осталось — redirect на `result/` |
| `POST` | `/gameplay/session/<session_id>/answer/` | Принимает ответ на текущий вопрос (id вопроса — скрытое поле формы), сохраняет `GameAnswer`, redirect на `play/` |
| `GET` | `/gameplay/session/<session_id>/result/` | Итоговый экран: счёт и разбор по `GameAnswer` |

Кнопка «Следующий вопрос» отдельного смысла не несёт — это просто сабмит формы ответа (`POST .../answer/`), которая сама решает, какой вопрос показать следующим, через redirect на `play/`. Отдельного «пропустить вопрос» эндпоинта не нужно — это тот же `POST .../answer/`, но без `selected_option`, что и так должно поддерживаться как штатный путь (истечение таймера на клиенте работает через авто-сабмит той же формы).

Так как в стеке уже используется HTMX, `POST .../answer/` можно обрабатывать двояко: обычный (non-HTMX) запрос отвечает `302` redirect на `play/` (полная перезагрузка страницы, рабочий сценарий и без JS); запрос с заголовком `HX-Request` вместо redirect сразу возвращает partial-шаблон следующего вопроса (или партиал итогового экрана, если вопросов не осталось), избегая лишнего round-trip'а. Логика вычисления "текущий вопрос" при этом остаётся общей и лежит в одном месте — во view, а не дублируется между обычным и HTMX-ответом.

### Мультиплеер
```
Хост создаёт комнату → получает ссылку-приглашение
    → Друзья переходят по ссылке
    → Все видят лобби (Django Channels / WebSocket)
    → Хост запускает игру
    → Вопросы синхронно появляются у всех
    → Счёт обновляется в реальном времени
    → Итоговая таблица лидеров
```

### Социальный сценарий
```
Лента новых викторин от подписок
    → Лайк / комментарий
    → Вызов друга на викторину
    → Сравнение результатов
```

## Архитектура запросов

| Тип запроса | Решение |
|---|---|
| Обычные страницы (список, профиль, лента) | Django sync views |
| AI-генерация викторины | Celery + Redis |
| Мультиплеер реального времени | Django Channels (WebSocket) |
| Кэш повторных AI-запросов | Redis cache |

---

## Важные практики производительности

1. **select_related / prefetch_related** — избегать N+1 запросов к БД
2. **Кэш AI-результатов** — одинаковые запросы (тема + сложность + кол-во) отдавать из Redis
3. **Пагинация** — не отдавать все викторины сразу, по 20 штук
4. **Индексы в БД** — на полях по которым часто фильтруем (category, author, is_public)
