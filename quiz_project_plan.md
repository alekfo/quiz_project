## Основные модели

### users/
- **User (кастомная модель, `AbstractUser`)** — `email` (unique), `ai_quizzes_generated`, `ai_quizzes_limit_per_day`, `is_subscribed`, `is_premium`, `email_confirmed`, `subscription_expires_at`. Отдельной модели `Profile` (аватар, bio, рейтинг, подписчики) пока нет — эти поля живут прямо на `User`; вынести в `Profile` имеет смысл, когда полей/данных станет заметно больше (например, при реализации Этапа 4 — подписки/лайки уже потребуют отдельных моделей `Follow`/`QuizLike`, но не обязательно `Profile`)

### quizzes/
- **Category** — название темы (история, наука, спорт, кино...)
- **Quiz** — название, описание, автор, тип (`ai` / `by_user`), категория (FK, `on_delete=PROTECT`), публичная/приватная (`status`, default `private`), `time_limit_seconds` (лимит времени на вопрос в секундах, задаётся автором при создании квиза, единый для всех вопросов — решение зафиксировано в разделе «Соло прохождение»: игрок это значение не выбирает, чтобы в будущем мультиплеере у всех участников партии было одинаковое время)
- **Question** — текст вопроса, порядок (`order`), интересный факт (`fact`, генерируется AI вместе с вопросом — отклонение от исходного плана: изначально это поле числилось за `AnswerOption` как «объяснение ответа», но Claude возвращает факт на уровне вопроса целиком, а не привязанным к конкретному варианту ответа, поэтому поле перенесено на `Question`)
- **AnswerOption** — варианты ответа, `is_correct`, `order`

### ai_generator/
- **GenerationRequest** — параметры (тема, кол-во вопросов, категория, сложность, стиль, аудитория), статус задачи, результат (`JSONField`)

### gameplay/
- **GameSession** — викторина (FK `Quiz`, `related_name="game_sessions"`), режим (`solo` / `multiplayer`), статус (`in_progress` / `completed` / `abandoned`, default `in_progress`), `started_at` (`auto_now_add`), `finished_at` (nullable), `created_by` (FK `User`, `on_delete=PROTECT`). `Meta.constraints` — частичный `UniqueConstraint(quiz, created_by, condition=status="in_progress")`, гарантирует на уровне БД, что у одного пользователя не может быть двух одновременных активных сессий на один квиз (закрывает TOCTOU-гонку, которая раньше решалась бы отдельной проверкой в коде). **Запланировано для Этапа 3**: поле `current_question` (FK `Question`, `null=True`) — используется только при `mode="multiplayer"`, единый «текущий вопрос» для всех участников партии; при `mode="solo"` остаётся `null`, текущий вопрос по-прежнему вычисляется индивидуально по истории `GameAnswer` участника (см. «Соло прохождение»)
- **GameParticipant** — сессия (FK `GameSession`, `related_name="participants"`), пользователь (FK `User`), `score` (default 0, инкрементируется атомарно через `F('score') + 1)`, не read-modify-write), `joined_at` (`auto_now_add`), `finished_at` (nullable — проставляется этому конкретному участнику, когда у него не осталось неотвеченных вопросов; для мультиплеера сессия в целом завершается только когда `finished_at` проставлен у всех участников). `UniqueConstraint(session, user)`
- **GameAnswer** — участник (FK `GameParticipant`, `related_name="participants_answers"`), вопрос (FK `Question`, `related_name="participants_answers"`), выбранный вариант (FK `AnswerOption`, `null=True`, `on_delete=SET_NULL` — намеренно не `CASCADE`: при редактировании квиза автор пересоздаёт все `AnswerOption` вопроса заново, `CASCADE` физически стирал бы историю уже сыгранных партий), `is_correct` (bool, `default=False`), `is_skipped` (bool, `default=False`), `shown_at` (`auto_now_add`, момент показа вопроса — точка отсчёта для серверной проверки таймера), `answered_at` (nullable, момент фактического ответа). `UniqueConstraint(participant, question)`. Строка создаётся уже в момент **показа** вопроса (`get_or_create`, не только при ответе) и служит единственным источником истины о прогрессе — отдельного поля-указателя «текущий вопрос участника» нет (в отличие от планируемого `GameSession.current_question`, который будет общим на всю партию, а не персональным)

### multiplayer/ *(модели реализованы; лобби почти готово — `create`/`detail`/`list`/`join`/`quit`/`set-quiz`/`confirm-ready` работают и с 2026-09-01 обновляются у всех участников живьём через WebSocket (`RoomConsumer`), `start` ещё нет, см. CLAUDE.md, сессии от 2026-08-20/24/25/2026-09-01)*
- **Room** — `title`, уникальный токен-приглашение (`token`), хост (FK `User`, `on_delete=SET_NULL`), `current_quiz`/`current_game_session` (FK, оба `null=True, blank=True`, меняются от раунда к раунду — `Room` персистентна, не одноразова, см. сессию от 2026-08-20). `current_quiz` выбирается хостом через `RoomQuizForm`, ограниченную его собственными квизами (`queryset=Quiz.objects.filter(user=host)`, выставляется в `__init__` формы); смена квиза сбрасывает `is_ready` всех `RoomPlayer`. Статус (`waiting` / `in_progress` / `finished`), `created_at`. **Отклонение от исходного плана**: хост при создании комнаты не становится `RoomPlayer` автоматически (создание закомментировано в `RoomCreateView`) — осознанно, хост может быть как играющим, так и чистым модератором; на `RoomDetailView` это учтено — общий блок лобби (список участников/готовности) виден при `is_host or is_player`, не только `is_player`
- **RoomPlayer** — комната (FK `Room`, `related_name="room_players"`), пользователь (FK `User`), `is_ready` (bool, `default=False`, переключается через `room_confirm_ready` — **одностороннее** подтверждение, `False → True`, без обратного действия игроком; сбрасывается в `False` только сменой `current_quiz` хостом), `joined_at`. `UniqueConstraint(room, user)`. Счёт **не** хранится здесь: как только хост стартует игру, на каждого `RoomPlayer` создаётся `GameParticipant` той же `GameSession` (та же модель, что и в соло) — `GameParticipant.score` остаётся единственным источником счёта, не дублируется

### social/
- **Follow** — подписки между пользователями
- **QuizLike** — лайки на викторины
- **Invite** — приглашение в комнату по ссылке

## Правило взаимодействия quizzes ↔ ai_generator

Направление зависимости — только одностороннее: **ai_generator зависит от quizzes, но не наоборот.**

- **quizzes** — «хранилище» сущностей викторины (`Quiz`, `Question`, `AnswerOption`). Ничего не знает о том, как викторина была создана — вручную или через AI. Отвечает только за хранение, отображение, каталог, прохождение.
- **ai_generator** — весь процесс AI-генерации целиком:
  - форма с параметрами запроса (тема, кол-во вопросов, сложность, стиль) — размещается **здесь**, а не в quizzes;
  - модель `GenerationRequest` (статус задачи, параметры, результат);
  - запрос к Claude API, промпты (`prompts.py`);
  - парсинг JSON-ответа и запись результата в модели quizzes (`ai_generator` импортирует `Quiz`/`Question`/`AnswerOption`, создаёт объекты через `quizzes/services.py`).

Смысл разделения: AI-функциональность можно отключить/заменить, не трогая ядро (quizzes). Ручное создание викторины (Этап 2) — это форма и view в самом quizzes, поскольку не требует Celery/внешнего API.

## Сценарии использования

### AI-генерация викторины
```
Пользователь заполняет форму (тема, кол-во, сложность, стиль)
    → Django создаёт GenerationRequest в БД
    → запрос к Claude API
    → Claude возвращает JSON с вопросами
    → пользователь получает formset с вопросами на правку (temp_ai_quiz.html)
    → сабмит → вопросы сохраняются в Quiz/Question/AnswerOption
    → пользователь попадает на превью квиза (quiz_preview.html)
    → публикует или оставляет приватной
```

**Текущее отклонение от плана**: запрос к Claude выполняется **синхронно** прямо внутри `ai_generator/views.py::index()`, без очереди Celery и без поллинга статуса — Celery в проекте пока не подключён вообще. Флоу с `GenerationRequest.status` + Celery-задачей + HTMX-поллингом остаётся целевой архитектурой (нужен, когда генерация станет заметно дольше текущей или появится нагрузка от нескольких пользователей одновременно), но для MVP синхронного вызова оказалось достаточно.

### Ручное создание викторины
```
Одна страница: форма викторины (название, категория, описание, аудитория, time_limit_seconds)
    + формсет вопросов (текст, порядок, факт, 4 варианта ответа, индекс правильного)
    → вопросы добавляются/удаляются динамически через JS без перезагрузки страницы
    → сабмит сохраняет Quiz + Question + AnswerOption одной транзакцией
    → превью викторины (quiz_preview.html)
    → публикация (переключение Quiz.status)
```

### Соло прохождение

Общий флоу:
```
Пользователь выбирает викторину из списка (свои + публичные)
    → POST на старт → создаётся GameSession (mode=solo, status=in_progress) + GameParticipant
    → redirect на экран прохождения
    → GET экрана прохождения вычисляет текущий вопрос:
        первый Question квиза (по order), для которого у участника
        ещё нет GameAnswer с answered_at != null ИЛИ is_skipped = True
        → если такого вопроса не осталось — redirect на итоговый экран
        → если есть — get_or_create GameAnswer(participant, question, defaults={shown_at: now()})
          (get_or_create — принципиально: если пользователь обновит страницу,
          shown_at не должен сброситься, иначе таймер обнуляется бесплатно)
          → рендер вопроса + клиентский JS-таймер на quiz.time_limit_seconds
          (по истечении клиентского таймера форма авто-сабмитится: form.requestSubmit())
    → пользователь выбирает вариант ответа, либо истекает клиентский таймер (авто-сабмит пустой формы)
    → POST ответа на тот же экран прохождения (см. таблицу ниже — отдельного endpoint под "ответ" нет)
        → сервер находит GameAnswer(participant, question); если answered_at уже проставлен — 403 (PermissionDenied)
          (защита от повторного сабмита формы, например через "назад" в браузере)
        → сверяет now() - shown_at с quiz.time_limit_seconds — если просрочено, ответ форсится как
          is_skipped=True/is_correct=False вне зависимости от того, что реально пришло в теле запроса
          (защищает от вручную остановленного/подменённого клиентского JS, не только от честного бездействия)
        → иначе сохраняет chosen_option, is_correct, answered_at = now()
        → обновляет GameParticipant.score атомарно (F('score') + 1), если ответ верный
        → redirect обратно на экран прохождения — цикл повторяется для следующего вопроса
    → когда неотвеченных/непропущенных вопросов не осталось:
        GameParticipant.finished_at = now(), GameSession.status = completed, GameSession.finished_at = now()
        → redirect на итоговый экран
    → итоговый экран: счёт участника, для мультиплеера (Этап 3) — также остальные участники
```

#### Координация по вопросам: URL-схема

Явного номера вопроса в URL нет — сервер всегда сам решает, какой вопрос показывать, исходя из истории `GameAnswer` участника (см. флоу выше). Если положить номер вопроса в URL (`/question/3/`), пользователь сможет вручную подкрутить его в адресной строке и перепрыгнуть вопрос или вернуться к уже отвеченному — состояние тогда пришлось бы валидировать отдельно, что просто дублирует ту же проверку, которую и так обязан делать сервер.

| Метод | URL | Что делает |
|---|---|---|
| `POST` | `/gameplay/quiz/<quiz_id>/start/` | Создаёт `GameSession` + `GameParticipant` (или, если у пользователя уже есть `in_progress`-сессия на этот квиз — переиспользует её), redirect на `play/` |
| `GET` | `/gameplay/session/<session_id>/play/` | Вычисляет и показывает текущий (первый неотвеченный) вопрос; если вопросов не осталось — завершает сессию/участника и redirect на `result/` |
| `POST` | `/gameplay/session/<session_id>/play/` | Принимает ответ на текущий вопрос (`chosen_option_id`, `current_answer_id` — скрытые поля формы), сохраняет `GameAnswer`, redirect обратно на `play/` |
| `GET` | `/gameplay/session/<session_id>/result/` | Итоговый экран: счёт и разбор по `GameAnswer` |

Отдельный `POST .../answer/` эндпоинт, который фигурировал в более ранней версии этого плана, решено не заводить — сдача ответа сабмитится тем же `POST` на `play/`, GET и POST на одном URL разведены по `request.method`. Кнопка «Следующий вопрос» отдельного смысла не несёт — это просто сабмит формы ответа, которая сама решает, какой вопрос показать следующим, через redirect на `play/`. Отдельного «пропустить вопрос» эндпоинта тоже нет — тот же `POST`, но без выбранного варианта (`chosen_option_id` пустой), что и так штатно обрабатывается как `is_skipped=True`.

**Не реализовано (осталось от исходного плана как возможная будущая оптимизация)**: HTMX-ветка, при которой `POST .../play/` в ответ на заголовок `HX-Request` сразу отдаёт partial-шаблон следующего вопроса вместо полного `302`-redirect. Сейчас всегда обычный redirect (рабочий сценарий и без JS). Стоит держать в уме при реализации мультиплеера ниже — там HTMX-поллинг того же рода понадобится не как опциональная оптимизация, а как обязательная часть флоу.

### Мультиплеер (Этап 3)

Два состояния, которые важно не путать (вопрос был явно поднят при обсуждении архитектуры):

- **Room (лобби)** — состояние *подготовки* к игре: кто в комнате, кто отметился готовым. Существует до того, как игра началась, и не имеет отношения к `GameSession`.
- **GameSession** — та же модель, что уже реализована и обкатана в соло-режиме. Для мультиплеера отличие только в том, что у одной `GameSession` несколько `GameParticipant` (по одному на каждого `RoomPlayer`), и появляется общее поле `current_question`.

Полный флоу *(создание/приглашение/готовность — реализовано и проверено вручную, см. CLAUDE.md сессии 2026-08-20/24/25; запуск раунда — реализовано 2026-09-02, см. CLAUDE.md той же датой)*:
```
Хост создаёт Room (title, host, статус waiting, invite-токен) — RoomCreateView
    → получает ссылку-приглашение (/multiplayer/rooms/<code>/)
    → друзья переходят по ссылке → "Стать участником" → создаётся RoomPlayer (room, user, is_ready=False) — room_join
    → хост выбирает викторину из своих квизов — room_set_quiz/RoomQuizForm → Room.current_quiz,
      сбрасывает RoomPlayer.is_ready=False у всех (смена квиза аннулирует старую готовность)
      (room_reset_quiz — симметричное действие хоста, сбрасывает Room.current_quiz обратно на None
      и тоже обнуляет готовность всех, если хочет выбрать квиз заново)
    → каждый участник подтверждает готовность (POST, одностороннее действие,
      обратного действия из UI нет) → room_confirm_ready → RoomPlayer.is_ready=True
    → экран лобби у всех участников обновляется без перезагрузки — WebSocket-пуш,
      см. отдельный раздел "WS — реализовано (лобби)" ниже (до 2026-09-01 был HTMX-поллинг,
      hx-trigger="every 2s", полностью заменён)
    → кнопка "Начать" видна только хосту и активна только когда все RoomPlayer.is_ready=True
      (проверка готовности — на бэкенде обязательна; фронтовая блокировка кнопки — только UX)
    → хост жмёт "Начать" → POST room_start → создаётся:
        GameSession(mode="multiplayer", quiz=room.current_quiz, room=room, created_by=host,
                     current_question=<первый Question квиза, по order>)
        + GameParticipant на каждого RoomPlayer комнаты (именно room_players — см. оговорку ниже
          про хоста-не-игрока)
      → Room.current_game_session = session, Room.status = in_progress, всё одной транзакцией
        вместе с _notify_room(room)
    → redirect всех участников на общий экран игры /gameplay/session/<id>/play/ — сам хост получает
      его как обычный HTTP-редирект от room_start, а игроки, которые просто сидят в открытом
      room_detail.html, узнают об этом через тот же WS-канал лобби (см. "WS — реализовано" ниже,
      RoomConsumer.room_update() теперь умеет слать не только статус, но и сигнал редиректа)
```

Хост при создании комнаты не становится `RoomPlayer` автоматически (осознанное решение — хост может быть модератором, не игроком, см. `multiplayer/` в разделе «Модели данных» выше); значит проверка готовности в `room_start` идёт по фактическому списку `RoomPlayer` комнаты, не привязываясь к тому, есть ли там хост. **Открытый вопрос, осознанно отложен пользователем 2026-09-02**: если хост не `RoomPlayer`, `room_start` не создаёт для него `GameParticipant` (цикл идёт только по `room.room_players.all()`) — значит его собственный переход на `gameplay:play` (и WS-редирект, который получит его же открытая вкладка лобби, т.к. `RoomConsumer.connect()` пускает по `is_host or is_player`) упрётся в `PermissionDenied` в `play()`. Планируемое решение — редиректить хоста-не-игрока сразу на `gameplay:result`, а не на `play`, но пока не реализовано.

**Ключевое отличие от соло внутри `play()`**: для `mode="multiplayer"` текущий вопрос **не** вычисляется индивидуально через `_get_questions_without_answer` (как в соло) — вместо этого `play()` напрямую читает `GameSession.current_question`. Все участники партии в любой момент времени видят один и тот же вопрос. Сохранение самого ответа (`_update_gameAnswer`, обновление `GameParticipant.score`) переиспользуется как есть — эта часть не завязана на режим. **Реализовано 2026-09-02**: `play()` сразу после общего поиска `participant`/проверки `PermissionDenied` расходится на `_play_solo`/`_play_multiplayer` — приватные хелперы, а не отдельные URL/view, чтобы `gameplay:play` осталась единой точкой входа (на неё и так уже ссылаются `room_start`/WS-редирект из лобби).

```
    → GET play/ (mode=multiplayer, _play_multiplayer) отдаёт session.current_question —
      один и тот же вопрос всем; get_or_create GameAnswer(participant, current_question) — как в соло,
      свой персональный shown_at на каждого участника (не общий "старт раунда" на всех, это
      сознательно не менялось — у каждого свой отсчёт с момента, когда лично он открыл вопрос);
      already_answered = bool(current_answer.answered_at or current_answer.is_skipped) — прокидывается
      в play.html, показывает "ВЫ УЖЕ ОТВЕТИЛИ, ЖДЁМ ОСТАЛЬНЫХ ИГРОКОВ" вместо формы ответа
    → игрок отвечает → POST play/ сохраняет GameAnswer как в соло (общий код, mode ни на что тут
      не влияет), и сразу после (тот же transaction.atomic()) — для mode="multiplayer" вызывается
      _check_and_advance_round(session.pk):
        select_for_update() на строку GameSession (гонко-безопасно — два почти одновременных
        сабмита не продвинут раунд дважды и не потеряют вопрос)
        → считает, у скольких GameParticipant есть GameAnswer.answered_at/is_skipped
          по текущему session.current_question
        → если не все — ничего не меняет
        → если все — current_question = следующий Question квиза по order, либо None,
          если вопросов не осталось (на следующем GET у любого участника это подхватывает
          уже существующий _check_and_make_complete — сессия завершается для всех разом,
          в отличие от соло, где участники завершают партию независимо друг от друга)
    → пока current_question не сменился, игроки, которые уже ответили и ждут остальных, должны
      как-то узнать о смене вопроса — **ещё не реализовано** (ни поллинг, ни WS для самого экрана
      игры; play.html лишь дизейблит кнопку по истечении личного таймера, дальше тишина до
      ручной перезагрузки страницы). Инфраструктура Channels/Redis Channel Layer для этого уже
      есть и обкатана на лобби (см. "WS — реализовано (лобби)" ниже) — вероятный путь: своя
      WS-группа на сессию (`session_<id>`, по аналогии с `room_<token>`), а не поллинг с нуля
    → после последнего вопроса — итоговый экран комнаты: таблица GameParticipant.score всех
      участников (result() уже реализован для mode=multiplayer с сессии от 2026-08-10 — собирает
      остальных участников сессии, см. CLAUDE.md; сортировки по убыванию очков пока нет, простой список)
```

**Сторож зависших игроков (после того как базовый цикл выше заработает — отдельный последующий шаг внутри Этапа 3)**: периодическая Celery beat-задача проходит по всем `GameSession(mode="multiplayer", status="in_progress")`, для каждой — по её `GameParticipant`, у которых на `current_question` есть `GameAnswer` без `answered_at`, а `now() - shown_at > quiz.time_limit_seconds` — форсит их ответ как `is_skipped=True, answered_at=now()` (тот же путь, что и клиентский авто-сабмит по таймауту в соло, просто инициированный не браузером игрока, а сервером). Это может стать той самой «последней» отметкой, разблокирующей продвижение `current_question` для всех. Страхует сценарий, где у игрока клиентский таймер не сработал (свёрнутая вкладка, зависший браузер, разрыв соединения) — без сторожа такая партия зависла бы навсегда в ожидании ответа, который никогда не придёт.

#### WS — реализовано (лобби, 2026-09-01; редирект в игру — 2026-09-02)

Полный разбор механики и найденных по пути багов — в CLAUDE.md (сессии от 2026-09-01/02) и в исходном учебном конспекте [`WS.md`](WS.md). Коротко, как это выглядит по факту:

- **ASGI** (`quiz_project/asgi.py`) — `ProtocolTypeRouter({"http": django_asgi_app, "websocket": AuthMiddlewareStack(URLRouter(multiplayer.routing.websocket_urlpatterns))})`. Обычные sync-view **не переписаны** на `async def` — HTTP-ветка это тот же Django, что и раньше.
- **`multiplayer/routing.py`** — `websocket_urlpatterns`, один маршрут `ws/multiplayer/rooms/<code>/` → `RoomConsumer`.
- **`multiplayer/consumers.py`** — `RoomConsumer(WebsocketConsumer)`, группа `room_<token>`. `connect()` проверяет право (хост или `RoomPlayer`, как в `_get_room_context`) и делает `group_add`. Внутри группы гуляет только сигнал `{"type": "room.update"}` **без HTML** — каждый подписанный `Consumer` сам перечитывает `Room` из БД и рендерит `_room_status.html` персонально под своего пользователя (`_room_status.html` зависит от того, чей это просмотр — общий на всех HTML был бы некорректен). Это осознанное отличие от «наивной» схемы, где view рендерит HTML один раз и рассылает всем.
- **`room_update()` с 2026-09-02 умеет два разных ответа**: сначала проверяет `room.status == "in_progress" and room.current_game_session_id` — если да, шлёт `{"type": "redirect", "url": reverse("gameplay:play", ...)}` и выходит (используется, когда хост запускает игру `room_start`); иначе — прежний JSON со статусом лобби (`html`/`can_confirm`/`is_ready`). Клиент (`room_detail.html`, `onmessage`) проверяет `data.type === "redirect"` первым делом и делает `window.location = data.url`. Реализовано вместо переиспользования старого `HX-Redirect` из мёртвого `room_status()` — тот был заточен под поллинг, которого для лобби больше нет.
- **Redis Channel Layer** (`channels_redis`) — тот же Redis, что и планировался под Celery/кэш, роль — pub/sub между обычным sync-view (изменил состояние) и `Consumer`'ами других игроков. Вьюхи (`room_join`, `room_set_quiz`, `room_reset_quiz`, `room_confirm_ready`, `room_start`, `RoomPlayerDeleteView.form_valid`) в конце вызывают `_notify_room(room)` → `async_to_sync(channel_layer.group_send)(...)`.
- **Важный практический нюанс, не был очевиден заранее**: `channels_redis==4.3.0` требует пиновать клиентскую библиотеку `redis` на `==4.6.0` — с более новыми версиями (проверено на `8.1.0`) долгоживущие WS-соединения падают по внутреннему таймауту `channels_redis`'а каждые ~5 секунд. См. CLAUDE.md, не поднимать `redis` в `requirements.txt` бездумно.
- Переход с поллинга на WS **не потребовал переделывать модели или бизнес-логику** — только добавление `_notify_room(room)` в конце нужных вьюх и замену клиентского `hx-trigger="every 2s"` на `new WebSocket(...)` в шаблоне.
- **Этот же канал пока обслуживает только лобби, не саму игру** — экран `gameplay/play.html` в мультиплеере остаётся без push/поллинга (см. чек-лист Этапа 3 выше и раздел «Мультиплеер» — открытый пункт про live-обновление экрана ожидания).

### Социальный сценарий
```
Лента новых викторин от подписок
    → Лайк / комментарий
    → Вызов друга на викторину
    → Сравнение результатов
```

## Архитектура запросов

| Тип запроса | Решение |
|---|---|
| Обычные страницы (список, профиль, лента) | Django sync views |
| AI-генерация викторины | Сейчас: синхронно в view. Целевая архитектура: Celery + Redis (см. отклонение в «Сценарии использования») |
| Мультиплеер реального времени | Лобби: Django Channels (WebSocket), реализовано, включая редирект в игру. Экран игры (`gameplay`, мультиплеерный `play()`): базовый цикл (общий вопрос, продвижение раунда) реализован обычными sync-view; live-обновление у ожидающих участников — поллинг/WS ещё не заводили |
| Кэш повторных AI-запросов | Redis cache |

## Важные практики производительности

1. **select_related / prefetch_related** — избегать N+1 запросов к БД
2. **Кэш AI-результатов** — одинаковые запросы (тема + сложность + кол-во) отдавать из Redis
3. **Пагинация** — не отдавать все викторины сразу, по 20 штук
4. **Индексы в БД** — на полях по которым часто фильтруем (category, author, is_public)
