# FRONTEND.md

Правила работы над внешним видом QuizApp. Читается перед любой фронт-задачей.
Фронтенд пишет Claude; бэкенд (`*.py`, миграции, настройки) пишет пользователь — см. «Граница с бэкендом».

Область действия: `templates/`, `*/templates/`, `static/css/`, `static/js/` (кроме `htmx.min.js`).

## Принятые решения (2026-10-01)

| Вопрос | Решение |
|---|---|
| Стили | Чистый CSS с переменными в `:root`. Без фреймворков, сборщиков, npm и CDN |
| Тема | Светлая и тёмная, переключение по системной настройке (`prefers-color-scheme`) |
| Адаптив | Mobile-first: базовые стили — под телефон, расширение через `@media (min-width: …)` |
| Характер | Игровой, яркий: насыщенные цвета, крупные кнопки, скругления, заметные состояния |
| Классы | Как сейчас — kebab-case по смыслу блока (`.btn`, `.room-list`, `.question-form`). Не BEM |
| JavaScript | Существующие inline-`<script>` в шаблонах не трогать; новый общий код — файлами в `static/js/` |
| Подтверждения | Перед страницей Claude коротко описывает, что собирается сделать; после «да» правит файлы сам и показывает результат |
| Порядок | Токены и `base.html` → меню → списки и превью → формы → лобби → игра |

## Стек и ограничения

- Django Templates + HTMX 2 (`static/js/htmx.min.js`, локальный файл) + чистый CSS + ванильный JS.
- Один общий `templates/base.html`, от него наследуются все страницы.
- Стили — только в `static/css/`. Не inline и не в `<style>` внутри шаблонов.
  Исключение: honeypot в `users/register.html` спрятан inline-стилем намеренно.
- Шрифты и иконки — без внешних запросов (системный стек шрифтов, эмодзи или inline-SVG).
  Подключение веб-шрифта — отдельное решение, файлы тогда кладутся в `static/`.

### Токены

Все цвета, отступы, радиусы, тени и размеры шрифта — CSS-переменные в `:root`. В правилах компонентов —
только `var(--…)`, без «голых» значений.

- **Цвета — по роли, а не по оттенку**: фон страницы, фон поверхности (карточки), основной текст, приглушённый текст,
  граница, акцент, акцент при наведении, текст на акценте, успех, ошибка, предупреждение.
- **Тёмная тема** — те же переменные, переопределённые в `@media (prefers-color-scheme: dark)`.
  Компоненты о теме не знают. Ручного переключателя пока нет.
- **Отступы** — одна шкала (шаг 4px), **радиусы** и **тени** — по 2–3 значения.
- **Типографика** — шкала размеров, базовый размер текста не меньше 16px (на телефоне меньше — нечитаемо,
  а поля ввода с меньшим шрифтом iOS зумит).

### Характер: игровой, яркий

- Один насыщенный акцентный цвет плюс цвета состояний (верно / неверно / ожидание).
- Варианты ответа и пункты разделов: высота области нажатия не меньше 44px. Обычные кнопки — 40px
  (решение пользователя от 2026-10-09: 44px выглядели громоздко).
- Заметные скругления, чёткие состояния `hover` / `focus-visible` / `active` / `disabled`.
- Анимации — короткие и по делу (нажатие, появление результата); уважать `prefers-reduced-motion`.
- Контраст текста и фона — не ниже 4.5:1 в обеих темах.

### Адаптив

- Базовые стили — для ширины от 360px, одна колонка.
- Брейкпоинты — только там, где раскладка реально меняется (ориентир: 640px и 1024px).
- Никакого горизонтального скролла страницы; широкие таблицы и списки прокручиваются внутри своего блока.
- Для mobile-first в `base.html` нужен `<meta name="viewport" content="width=device-width, initial-scale=1">` —
  сейчас его нет, добавляется на первом шаге. Там же `lang="en"` → `lang="ru"`.

### Компоненты

Каждый компонент — один класс и модификаторы отдельными классами (`.btn`, `.btn-primary`, `.btn-danger`).
Перед созданием нового класса — проверить, нет ли подходящего в `static/css/main.css`.

Базовый набор: кнопка (обычная / главная / опасная / disabled), карточка, поле формы с подписью и ошибкой,
flash-сообщение (`.messages li.success` / `.error`), список, шапка, таймер, спиннер, вариант ответа.

## Контракты с бэкендом — не ломать

Менять внешний вид и структуру разметки можно свободно. Перечисленное ниже нельзя переименовывать,
удалять или переносить без согласования: на это завязаны вьюхи, JS, HTMX или WebSocket.

### Общее

- В каждой `<form method="post">` — `{% csrf_token %}`.
- `name` полей, `action` и `method` форм не менять. Поля рендерить через объекты формы Django
  (`{{ form.field }}`, `{{ form.field.errors }}`), а не писать `<input>` вручную.
- Действия, меняющие данные, — только `<form method="post">` + `<button>`, не `<a href>`
  (вьюхи закрыты `require_POST`, ссылка даст 405).
- Имена маршрутов в `{% url %}` и имена переменных контекста не менять.
- Не добавлять в шаблоны логику доступа: что показывать, решает контекст из вьюхи.
- Атрибут `hidden` — рабочий механизм показа/скрытия блоков из JS. Не перебивать его
  CSS-правилом вида `display: flex` на том же элементе без `[hidden] { display: none }`.

### `templates/base.html`

- `<ul class="messages">` внутри `.container-header-messages` — рендерится всегда, даже пустой:
  в него пишут `base.js` (`showToast`) и кнопка копирования ссылки в `room_detail.html`
  (она ищет `.messages`, а при отсутствии создаёт его в `.container-header-messages`).
- Подключение `static/js/base.js` — в `<head>` **без `defer`**: скрипт ставит класс `.js` на `<html>` до отрисовки
  (без JS список разделов на телефоне виден всегда, с JS — только по бургеру). После него — `htmx.min.js`.
- `#nav-toggle` (бургер, `aria-controls="site-nav"`, `aria-expanded`) и `#site-nav` (класс `.is-open`) — связка для `base.js`.
- Подсветка текущего раздела — по `request.resolver_match.namespace` / `url_name` в шаблоне; при добавлении нового
  приложения или раздела условие в `base.html` нужно дополнить.
- `.header-main` — общий «ряд с разнесёнными краями», используется и в шапке, и в `room_detail.html`;
  стили шапки вешать на `.site-header .header-main`, а не на сам класс.
- Блоки `{% block title %}` и `{% block body %}`.
- Форма выхода и форма «Связаться с поддержкой» — POST-формы, остаются формами.

  - `temp_ai_quiz.html` (статус `completed`) — контекст `formset`, `gen_request`, `series_id`, `res`. Параметры
    раунда в шапке берутся из `gen_request` (`get_level_display` и т.п.), `res` шаблон не читает.

    на месте). Карточки вопросов лежат в `.question-cards` (тот же вид, что в `quiz_form.html`, без добавления

### Игра — `gameplay/play.html`

Переделка сделана 2026-10-27 в два шага: разметка, стили и JS; затем ответ через HTMX и движение.
Inline-скрипта на странице больше нет, весь JS — `static/js/play.js` (подключён в конце `{% block body %}` с `defer`).

- **Контекст** (единый GET `play` для трёх ролей): `mode`, `role` (`player` / `host_observer`), `current_session`,
  `current_question`, `question_number`, `question_count`, `is_last_question`, `can_advance`; игроку — `current_answer`,
  `already_answered`, `points_gained`, `score`, `streak`, `answers_progress` (`state`: correct / wrong / skipped /
  current / pending), `remaining_seconds`; в мультиплеере — `participants_count`, `answered_count`, `all_answered`.
- **`#play-main`** — карточка `.card.play-card`, весь экран. `data-question-id` (сверка с WS),
  `data-session-socket` (только мультиплеер), `data-remaining` / `data-time-limit` (только игроку до ответа).
  Будущая цель HTMX-подмены (шаг 2) — не дробить.
- **Ответ через HTMX** — на `#answer-form` `hx-post` (тот же `play`), `hx-target="#play-main"`, `hx-select="#play-main"`,
  `hx-swap="outerHTML"`, `hx-sync="this:drop"`: HTMX проходит по редиректу на GET `play` и подменяет блок целиком,
  **страница и WS-соединение остаются**. Поэтому `play.js` всё внутри `#play-main` находит заново в `init()` после
  каждой подмены (событие `htmx:load` с `elt.id === "play-main"`), а `document.getElementById('play-main')` берёт
  каждый раз, не кэшируя. Ответ пришёл не со страницы `play` (раунд закончился) — `htmx:beforeSwap` отменяет подмену
  и делает обычный переход. Ошибка запроса — тост из `base.js`, кнопка «Ответить» снова доступна.
  «Следующий вопрос» — по-прежнему обычная POST-форма с перезагрузкой. Без JS — обычная отправка обеих форм.
- **Ответ** — `#answer-form` (POST на `gameplay:play`), `input[name="chosen_option_id"]` внутри `label.option-card`
  (радиокнопка `.option-input` скрыта, но в фокусе), `input[name="current_answer_id"]`, `#submit_button`
  (неактивна, пока вариант не выбран — делает JS; без JS активна). Цифры 1–N выбирают вариант, Enter отвечает.
  На нуле таймера `requestSubmit()` — без выбора сервер засчитывает пропуск.
- **Полоса времени** — `#timer` (`.timer`, классы `.is-warning` ≤ 50 %, `.is-danger` ≤ 25 %), `.timer-track[role=progressbar]`,
  `.timer-fill` (ширину ставит JS), `#timer-seconds`. Только игроку до ответа.
- **Вердикт** — `.verdict.is-correct` («Верно! +N», `points_gained`) / `.is-wrong` («Неверно») / `.is-timeout`
  («Время вышло» — `is_skipped`: у игрока пропуск бывает только по таймеру, при пропуске ведущим вопрос сразу
  переключается). Выбранный вариант — `.option-card.is-static.is-chosen` с меткой «Ваш ответ». **Верный вариант
  игроку не выводится ни классом, ни атрибутом** — `option.is_correct` читается только в ветке `host_observer`
  (закреплено тестами `PlayContextTests.test_player_never_sees_which_option_is_correct` и
  `MultiplayerFlowTests.test_host_moderator_watches_game_without_answer_rows`).
- **Ведущий-наблюдатель** — варианты `.option-card.is-static`, верный — `.is-correct` + `.tag-success` «Верный ответ»;
  метка «Ведущий» вместо счёта, без таймера. Факт виден ему сразу (может прочитать вслух), игроку — после ответа.
- **Метки у варианта** («Ваш ответ», «Верный ответ») — внутри `.option-text`, под текстом: справа они сжимали
  текст и рвали слова.
- **Шапка** — `.play-header`: «Вопрос N из M» (`.play-step`), точки `ol.answer-dots` / `.answer-dot.is-<state>`
  (текущая позиция — `.is-now`, кольцо акцентом), счёт `.play-score-value`, серия — `.tag.tag-warning`
  «Серия: N подряд» (от 2).
- **Дальше** — `#next-form` (POST на `gameplay:next_question`, скрытое `question_id`), кнопка `#next-button`
  с `data-label-next` («Следующий вопрос» / «К результатам»). Только при `can_advance`. У ведущего в мультиплеере —
  атрибуты `data-host`, `data-all-answered`, `data-answered`, `data-participants`: пока ответили не все, JS пишет
  «Пропустить ожидание (N не ответили)», первое нажатие меняет надпись на «Точно пропустить? Нажмите ещё раз»
  (`.btn-danger`, 4 с), второе отправляет. Без JS — «Пропустить ожидание», отправка сразу. Игрок мультиплеера после
  ответа видит `.play-waiting` «Ждём, пока ведущий переключит вопрос».
- **Кто ответил** — partial `gameplay/_players_status.html`, корень `section#waiting-info` (мультиплеер, всем ролям,
  всегда). Рендерится и в `play.html`, и в `GameSessionConsumer.session_update` — новые переменные в нём нужны в обоих
  местах (`user` в консьюмер передаётся явно). «Думает» выводится всегда, при найденном ответе прячется CSS
  (`.players-status-row:has(.players-status-done)`) — флага «ответил» на участника в контексте нет.
- **WebSocket** (`play.js`): `redirect` — переход; `status` — замена `#waiting-info`, подпись кнопки ведущего по
  `answered_count` / `participants_count` / `all_answered`; `current_question_id` ≠ вопросу страницы — перезагрузка.
  Сразу после подключения консьюмер присылает снимок состояния тем же форматом (`redirect` или `status`) — так
  страница узнаёт о конце раунда или смене вопроса, случившихся, пока она грузилась (сигнал до подключения теряется).
  Обрыв — `#play-connection` (общий стиль с `.lobby-connection`).

- **Движение** (исключения из правила о движении, CSS — внутри `@media (prefers-reduced-motion: no-preference)`,
  «+N» JS не запускает при reduced-motion). Только сразу после ответа через HTMX: `play.js` ставит на `#play-main`
  `.is-revealed` (вердикт «выпрыгивает» за 0,35 с, факт проявляется с задержкой 0,5 с) и `.is-flash-correct` /
  `.is-flash-wrong` (карточка на 1 с заливается цветом вердикта с кольцом, `@keyframes play-flash`; таймаут — без
  вспышки). При F5 на экране вердикта классов нет — всё стоит спокойно. «+N»: `.verdict.is-correct[data-points]`,
  метка `.score-gain` слева от `.play-score-value`, число досчитывает за 0,7 с и вспыхивает (`.is-flash`, общий
  `@keyframes score-flash`). Последние 5 с — `.timer.is-ending`: полоса пульсирует, секунды красные (цвет — и при
  reduced-motion).

#### Решения по переделке `play.html` (пользователь, 2026-10-26)

Выполнены по плану «бэкенд (пользователь) → тесты → фронт» (временный план удалён 2026-10-27, итог — в этом разделе
и в `quiz_project_plan.md`, раздел «Игра с экраном вердикта»).

- **Механика.** Один указатель `GameSession.current_question` для соло и мультиплеера. Вопрос → «Ответить» →
  экран вердикта, указатель стоит на месте → «Следующий вопрос» (POST `gameplay:next_question` с `question_id`)
  → следующий вопрос; на последнем — «К результатам». Кнопку жмёт: соло — сам игрок после ответа; мультиплеер —
  только хост (неиграющий — всегда, играющий — после своего ответа). Состояние экрана выводится из базы — F5
  оставляет на том же экране.
- **Вердикт.** «Верно! +N» / «Неверно» / «Время вышло», мягкая заливка экрана зелёным / красным (таймаут —
  нейтрально), цвет всегда дублируется значком и текстом; затем плавно проявляется факт вопроса. **Верный вариант
  при ошибке не показывается** — только факт как подсказка (как и в `result.html`). Вспышка — только сразу после
  ответа (подмена блока через HTMX); при F5 на экране вердикта — заливка без вспышки.
- **Таймер** — убывающая полоса во всю ширину, цвет плавно зелёный → жёлтый → красный по доле оставшегося
  времени, последние ~5 с — лёгкая пульсация; рядом мелкое число секунд (для доступности и дальтоников).
  У ответившего полоса останавливается и прячется. Автоотправка на нуле — как сейчас.
- **Ответ** — «выбрал вариант → Ответить» (не в один тап). Варианты — крупные карточки вокруг сохранённых
  радиокнопок `chosen_option_id`; клавиши 1–4 и Enter.
- **Шапка игры**: «Вопрос N из M» + точки по ответам (верно / неверно / пропущено / текущий / впереди), счёт
  с выезжающим «+N» (по образцу `score-gain.js`), «Серия: N подряд» (только визуально, на очки не влияет).
- **Мультиплеер.** «Ответили N из M» и список игроков (`_players_status.html`) обновляются по WS. Игрок без кнопки
  видит «Ждём, пока ведущий переключит вопрос». У хоста, пока ответили не все, кнопка называется
  «Пропустить ожидание (N не ответили)» — подтверждение двухшаговой кнопкой на странице (без `window.confirm`),
  неответившие получают «пропущено». Отдельной кнопки «пропустить зависших» нет.
- **Неиграющий ведущий** теперь попадает в игру, а не в лобби: видит вопрос и варианты без выбора, **верный вариант
  подсвечен**, кто ответил, кнопку «Следующий»; таймера нет. Игроку признак верного варианта в HTML не попадает
  ни в каком виде. В лобби во время раунда «Вернуться в игру» показывается и хосту.
- **Движение** — три новых исключения из правила «движение только у иконок разделов»: вспышка вердикта, пульсация
  полосы времени, «+N» к счёту в игре. При `prefers-reduced-motion` — без вспышки, пульсации и выезда.
- **Не делаем**: аватары игроков на экране игры, вибрация на телефоне; на будущее (меняют правила игры) — бонус
  за скорость ответа, запас 1–2 с к серверному таймауту.

  на HTMX-запрос возвращают его с тем же контекстом. Новая переменная в partial — значит, новый ключ
  в `get_follow_context`, а не в одной вьюхе.
- На своём профиле (`is_it_me`): кнопки подписки нет, вместо неё ссылка в «Мой профиль»; список квизов не выводится.
  Счётчик подписчиков виден всегда.
- Карточки квизов — та же `.quiz-card`, что в коллекции. Серии без раундов в список попадают («Раундов: 0»).

### Пользователи — `users/users_list.html`, `users/_user_rows.html`

- Контекст из `UsersListView`: `users` (результаты поиска или мои подписки), `q` (запрос после `strip()`),
  `is_search` (запрос не короче 2 символов), `followers` (кто подписан на меня — только когда `is_search` ложно).
  Случай «один символ» — `q and not is_search` (подсказка над вкладками).
- Поиск — GET-параметр `q`, поле `name="q"`. Без JS — обычная форма. С HTMX: `hx-get` на тот же URL,
  `hx-trigger="input changed delay:300ms from:find input, submit"`, `hx-target="#user-results"`, `hx-swap="outerHTML"`,
  `hx-push-url="true"`, `hx-sync="this:replace"`.
- На HTMX-запрос вьюха отдаёт только `users/_user_rows.html` (`get_template_names`). У него **один корень**
  `<div id="user-results">` — он подменяется целиком; всё, что должно обновляться при поиске, — внутри него,
  форма поиска — снаружи (иначе поле теряло бы фокус при каждом ответе).
- **«Назад» после живого поиска**: на форме `hx-history="false"` — HTMX не хранит копию страницы,
  и при возврате срабатывает `refreshOnHistoryMiss` (`<meta name="htmx-config">` в `base.html`): страница
  перезагружается целиком обычным GET. Без этого HTMX восстанавливал бы старую копию HTML (пустое поле поиска,
  вкладки без обработчиков), а при её отсутствии запрашивал бы адрес с `HX-Request` и получал один partial.
  Любой новой странице с `hx-push-url` нужно то же самое.

### Комнаты — `multiplayer/room_list.html`

- Контекст из `RoomListView` (`TemplateView`): `participant_room` — незакрытая комната, где пользователь игрок
  (один `Room` или `None`), `hosted_rooms` — незакрытые комнаты, где он хост, без `participant_room`,
  `finished_rooms` — закрытые, где он хост или игрок. У каждой комнаты `current_series` подгружена через
  `select_related` и есть аннотация `players_count`: в шаблоне не заменять на `room.room_players.count` /
  `.all|length` (тест `RoomListTests.test_query_count_does_not_grow_with_rooms` ловит рост числа запросов).
- Вкладки — тот же `.tabs` + `tabs.js`, панели `#active` и `#finished` (попадают в адрес). Счётчик «Активные» —
  `hosted_rooms|length` плюс 1, если есть `participant_room`; `|length` вычисляет QuerySet и кэширует его,
  цикл ниже второго запроса не делает.
- Во вкладке «Активные»: блок «Вы участник» (`participant_room`, метка «Вы хост», если он же хост), затем «Вы хост»;
  пустое состояние — только если пусто и то и другое. В «Завершённых» метка роли «Вы хост» / «Участник» —
  по `room.host_id == user.id` (отображение, не правило доступа; кто попадает в список, решает вьюха).
- Комната ведёт в лобби по `room.token` (`multiplayer:room_detail`, параметр `code`).

## Граница с бэкендом

- **Сначала бэкенд, потом фронтенд** (решение пользователя от 2026-10-09). Если перед шагом или по ходу него
  в `*.py` были правки — сначала проверить их (чтение + `python manage.py test`) и сообщить результат.
  Пока в бэкенде есть ошибка или нерешённый вопрос, шаблоны, CSS и JS не трогать: остановиться, описать проблему,
  дождаться, пока пользователь её закроет. Это относится ко всем разделам «Контрактов» выше.
- Если задаче нужна правка в `*.py` (новая переменная контекста, новый URL, partial-ответ вьюхи) —
  Claude не правит сам: останавливается, описывает, что нужно, пользователь делает.
- Вынос существующего inline-JS в файлы, переименование id/классов из раздела «Контракты» —
  только по отдельному согласованию.
- Коммиты и пуши делает пользователь.

   live-обновления работают.
6. Показать результат. Новое решение по дизайну (токен, компонент) — дописать в этот файл.
