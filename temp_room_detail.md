## Как устроено лобби сейчас (чтобы было понятно, что меняем)

Страница собирается из двух кусков:

- **`room_detail.html`** — рендерится один раз обычным GET (`RoomDetailView`). В нём всё, где есть формы
  (`{% csrf_token %}`): готовность, выбор / сброс квиза, старт, вход / выход.
- **`_room_status.html`** (корень `#room-status`) — включается в страницу при GET, а потом **перерисовывается
  по WebSocket**: `RoomConsumer.room_update` на каждое событие комнаты рендерит его через `render_to_string`
  **без `request`** и шлёт HTML + набор флагов. JS страницы заменяет `#room-status` целиком и по флагам
  переключает `hidden` у форм из `room_detail.html` (самих форм по WS не прислать — нет CSRF-токена).

Контекст для **обоих** путей строит одна функция — `multiplayer/views.py::_get_room_context(context, room, user)`.
Отсюда главное правило этого плана: **новая переменная для шаблона добавляется в `_get_room_context`**, тогда
она появится и при GET, и в WS-рендере. А флаг, который нужен JS (а не шаблону), надо ещё **явно** положить
в `payload` в `consumers.py::room_update` — туда попадает только то, что перечислено руками.

И второе: `_get_room_context` вызывается **на каждое WS-событие для каждого подключённого** — всё, что в ней
считается, должно браться из уже загруженных (`prefetch_related`) данных, а не новыми запросами. Иначе 5 игроков ×
каждое нажатие «Готов» = лавина запросов. Поэтому ниже везде «посчитать в Python по `room.room_players.all()`»,
а не `.count()` / `.filter()`.

## Шаг 1. `room_join` — только POST (решение 6)

**Проблема.** Сейчас вход в комнату — ссылка `<a href=".../join">`, вьюха меняет данные по GET. Любая чужая
страница может вставить `<img src="https://наш-сайт/multiplayer/rooms/<code>/join">` — браузер залогиненного
пользователя выполнит GET со своими cookie, и пользователь окажется участником чужой комнаты. CSRF-защита Django
действует только на POST, поэтому правило проекта: «меняет данные — только POST-форма».

**Что сделать.**

- Добавить `@require_POST` к `room_join` (порядок как у остальных: `@login_required` сверху, `@require_POST` под ним).
- Больше ничего: шаблон с формой и `{% csrf_token %}` сделаю я.

**Заодно (пункт из `TODO.md` от 2026-10-19, по желанию — там же и закрыть):** проверка «уже участник другой
активной комнаты» не исключает текущую — при повторном входе в свою же комнату сообщение говорит про «другую».
Добавить в эту проверку `.exclude(token=code)`. Тогда повторный вход дойдёт до `except IntegrityError`
и покажет правильное «Вы уже участвуете в этой комнате».

## Шаг 2. Порядок игроков

**Проблема.** У `RoomPlayer` нет `Meta.ordering`, а `prefetch_related("room_players__user")` порядок не задаёт.
База вправе отдавать строки в любом порядке — после каждого обновления по WS список игроков может перескакивать.

**Варианты.**

- **(рекомендую) `Meta.ordering = ["joined_at", "pk"]` на `RoomPlayer`.** Действует на все запросы игроков
  разом — и в `RoomDetailView`, и в консьюмере, и в будущих местах. `pk` — вторым ключом на случай одинакового
  `joined_at`. Нужна миграция (`AlterModelOptions` — схему таблицы не меняет, только состояние модели) —
  `makemigrations` / `migrate` запускаете вы.
- `Prefetch("room_players", queryset=RoomPlayer.objects.select_related("user").order_by("joined_at"))`
  в каждом месте, где грузится комната. Без миграции, но мест два (`RoomDetailView` и консьюмер), и третье
  место его забудет.

Как работает `Meta.ordering` с prefetch: Django делает отдельный запрос `SELECT ... FROM roomplayer WHERE room_id IN (...)`
и к нему применяется `ordering` модели — так что порядок сохранится и в `room.room_players.all()` из кэша.

## Шаг 3. Готовность и кнопка «Начать игру» (решение 3)

**Проблема.** `can_start_round` = «квиз выбран, серия не завершена, раунд не идёт» — **без** проверки игроков.
А `room_start` отказывает, если игроков нет или кто-то не готов. Хост видит кнопку, жмёт — получает тост с ошибкой.

**Что нужно шаблону и JS.** Два разных вопроса — «показывать ли блок старта» и «можно ли нажать»:

| Переменная | Значение |
|---|---|
| `players_count` | сколько `RoomPlayer` в комнате |
| `ready_count` | сколько из них `is_ready` |
| `start_available` | квиз выбран **и** раунд сейчас не идёт (`room.current_game_session is None`) — блок старта виден |
| `can_start_round` | `start_available` **и** `players_count > 0` **и** `ready_count == players_count` — кнопку можно нажать |

Счётчики — по уже загруженному `room.room_players.all()`, без новых запросов:

```python
players = list(room.room_players.all())
ready_count = sum(1 for p in players if p.is_ready)
```

`room.current_series_run.status != "completed"` из старого условия можно убрать: при завершении серии
`_check_and_make_complete` обнуляет и `current_series`, и `current_series_run` — до `start_available` тогда
не дойдёт (квиз не выбран). Если оставите для подстраховки — тоже не ошибка.

**Важно:** проверки в `room_start` **не убирать**. Флаг в контексте — только про то, что показать; кто угодно
может отправить POST руками, правило остаётся на сервере. Получится, что условие живёт в двух местах — это нормально
(отображение / защита), но если поменяете одно, проверьте второе.

**В `consumers.py::room_update`** — добавить в `payload` `players_count`, `ready_count`, `start_available`
(`can_start_round` там уже есть). Без этого JS не сможет обновить подпись «Ждём готовности: 2 из 3» на лету,
когда игрок нажал «Готов».

**Тесты упадут** — это ожидаемо: `test_can_start_round_depends_on_series_and_active_round` (в нём нет игроков —
теперь `can_start_round` будет `False`) и проверка состава ключей WS-сообщения в тесте консьюмера. Не подгоняйте,
обновлю я (шаг 8).

## Шаг 4. «Сменить квиз» через подтверждение, если серия уже начата (решение 5)

**Проблема.** `room_reset_series` переводит идущий прогон в `abandoned`: раунды, сыгранные в этой серии,
перестают быть «текущей игрой» (остаются только в «Истории игр»). Сейчас это одна кнопка без вопроса.

**Как сделать** — по образцу `room_close` (GET — страница подтверждения, POST — действие):

1. Декоратор `@require_POST` → `@require_http_methods(["GET", "POST"])` (`django.views.decorators.http`).
2. Проверку `room.host != request.user` оставить **до** ветвления — она нужна обоим методам.
3. `if request.method == "GET":` → `render(request, "multiplayer/room_reset_confirm.html", {"room": room, ...})`.
   В контекст — что потеряется: например `completed_rounds` (число завершённых раундов текущего прогона).
   Посчитать можно по `room.current_series_run.game_sessions` — но тогда добавьте в `get_object_or_404`
   `select_related("current_series", "current_series_run")`. Если прогона нет (`current_series_run is None`) —
   GET можно просто редиректить в лобби: подтверждать нечего.
4. POST — как сейчас.
5. В `_get_room_context` — флаг `series_run_started = room.current_series_run is not None`.
   Шаблон по нему решает: прогон есть → «Сменить квиз» — ссылка на GET-подтверждение; нет → POST-форма сразу.

Почему флаг достаточно отрисовать при GET, а не слать по WS: прогон создаётся только в `room_start`, который
делает редирект (хост попадает на страницу заново), а обнуляется при смене / сбросе квиза (тоже редирект)
или при завершении серии (тогда квиз сбрасывается, и блок «Сменить» скрыт целиком). Состояния «прогон появился,
а страница хоста не перезагрузилась» не бывает. В payload добавлять не нужно.

Шаблон страницы подтверждения сделаю я (тот же `.confirm-card`, что у удаления квиза).

## Шаг 5. Прогресс серии списком раундов — `gameplay/services.py::get_series_progress`

**Зачем.** В новом лобби прогресс — список раундов: пройденные (со ссылкой на результат), текущий (с меткой
«Идёт», если раунд уже играют), остальные — приглушённо. Сейчас функция отдаёт только `completed_sessions`
и `current_round` — из этого не собрать «какие раунды ещё впереди». А лидерборд в шаблоне делает
`series_run.series.rounds.count` в цикле — запрос на каждую строку.

**Что добавить в возвращаемый словарь** (старые ключи не трогать — `_series_progress.html` общий с `solo_room`,
и тесты на них есть):

- `rounds_progress` — список по раундам серии в порядке `round_order`, у каждого элемента:
  - `round` — объект `Quiz` (название раунда — `round.subject`);
  - `state` — `"completed"` / `"current"` / `"pending"`;
  - `session` — завершённая `GameSession` этого раунда (для ссылки на результат) или `None`.
- `rounds_count` — `len(...)` того же списка (вместо `rounds.count` в шаблоне).

Как собрать без лишних запросов:

```python
rounds = sorted(series_run.series.rounds.all(), key=lambda r: r.round_order)
completed_by_quiz = {s.quiz_id: s for s in completed_sessions}
```

и дальше в цикле: есть в `completed_by_quiz` → `completed`; `round_order == series_run.current_round_index`
(и не завершён) → `current`; иначе `pending`.

Почему `sorted(... .all())`, а не `.order_by("round_order")`: `.order_by()` строит **новый** запрос и
игнорирует prefetch-кэш (в консьюмере `current_series_run__series__rounds` уже подгружены). `sorted` по кэшу
бесплатен. Тот же приём, что `|dictsort` в `quizseries_detail.html`.

Почему по `round_order`, а не «индекс в списке»: после удаления раунда в `round_order` бывают дырки — это уже
учтено в `_advance_series_run` (2026-09-14), здесь то же самое.

Нужно, чтобы `series_run.series.rounds` был подгружен там, где функцию зовут: в консьюмере уже есть
(`current_series_run__series__rounds`), в `RoomDetailView` — добавить (шаг 6), в `solo_room` — проверьте
`prefetch_related` вьюхи; если нет, будет один запрос на страницу, не в цикле — терпимо, но лучше добавить.
