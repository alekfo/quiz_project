# pitfalls-check

Это не замена `/code-review` — это узкий, специфичный для *этой* кодовой базы чек-лист. Каждый пункт ниже — реально случавшийся баг (не гипотетический), см. ссылки на `CLAUDE.md`/`TODO.md`. Применяй при чтении диффа: для каждого пункта — реально проверь код на этот конкретный паттерн, не пропускай молча.

## Чек-лист

1. **Nullable FK разыменован без проверки.** Ищи `obj.field.attr`, где `field` — `ForeignKey(..., null=True)`. Модели с такими полями в проекте: `GameSession.room` (null для `mode="solo"`), `Room.current_series`/`current_series_run`/`current_game_session`, `SeriesRun.room` (null для соло-прогонов). Пример реального бага: `session.room.host` в `gameplay/views.py::result()` — `AttributeError` на любом соло-раунде (найдено 2026-09-28). Правило: перед обращением к атрибуту через nullable FK — либо `if obj.field:`, либо `obj.field.attr if obj.field else default`.

2. **`.update()` вызван на инстансе модели вместо `.save()`.** `.update()` существует только у `QuerySet`/related-менеджера (`obj.related_set.update(...)`), а не у объекта, полученного через прямой `ForeignKey`-дескриптор (`room.current_series_run.update(...)` — не сработает, `room.current_series_run` это инстанс `SeriesRun`, не менеджер). Правильно: `instance.field = value; instance.save(update_fields=[...])`. Путаница обычно возникает из-за соседства с настоящими related-менеджерами (`room.room_players.update(...)` — это ОК, `room_players` действительно менеджер).

3. **FK присвоен сырым значением по имени связи вместо `_id`.** `obj.category = "3"` или `obj.category = some_pk` падает `ValueError` — по имени связи (`category`) Django ждёт инстанс модели. Если под рукой только `pk`/строка — присваивать через `obj.category_id = value`. Обратный случай тоже встречался: `series=series_id if series_id else series_id` — тождественный тернарник, ничего не решает, нужно реально различать "есть pk существующей записи" от "нужно создать новую".

4. **`RelatedManager` используется напрямую вместо `.all()`.** `for x in room.room_players:` или `any(p for p in room.room_players)` — `TypeError: 'RelatedManager' object is not iterable`. Всегда `room.room_players.all()`. Встречалось несколько раз в разных функциях `multiplayer/views.py`/`gameplay/views.py` — при чтении диффа целенаправленно ищи голые обращения к related-менеджеру без `.all()`/`.filter()`/`.exists()`/`.count()` сразу после имени.

5. **Забытый `.first()` / случайный лишний `.first()`.**
   - Забытый: `qs.filter(...)` присвоено туда, где ожидается один инстанс (например, `FK` при `create()`) — `ValueError: Cannot assign "<QuerySet ...>"`.
   - Лишний и вредный: `related_manager.first()` без `Meta.ordering` на модели молча клонирует queryset через `order_by('pk')` — клон **не наследует** уже загруженный `prefetch_related`-кэш, что даёт лишний SQL-запрос на каждую итерацию цикла, если это происходит внутри цикла. Если queryset уже prefetch-нут и важно не терять кэш — бери `qs.all()[0]` (слайсинг), а не `.first()`.

6. **Позиционная арифметика вместо фильтрации по значению поля, когда возможны дыры в последовательности.** `current_round_index + 1` в сравнении с `rounds.count()` — ломается, если раунд удалён из середины без переиндексации `round_order`. Правильный паттерн, уже принятый в проекте: `qs.filter(order_field__gt=current_value).order_by('order_field').first()` (см. `_advance_series_run`, `_check_and_advance_question`). Применяй тот же вопрос к любому новому коду, который вычисляет "следующий" элемент по индексу/count, а не по значению.

7. **Один `except IntegrityError` обслуживает два разных unique-constraint'а.** Если в блоке `try` создаются две разные записи с разными констрейнтами (например, `SeriesRun` и `GameSession` в одной функции), один общий `except IntegrityError: return Model.objects.get(...)` может попытаться восстановить не ту сущность, которая реально вызвала конфликт — `DoesNotExist` вместо вменяемой обработки гонки. Разводи на отдельные `try/except` по каждому создаваемому объекту с его собственным `.get()`.

8. **Статус/флаг переиспользуется без проверки, как он уже трактуется в других местах.** В проекте есть устоявшаяся трёхстатусная семантика `SeriesRun.status` (`in_progress`/`completed`/`abandoned`) — `"abandoned"` означает именно "прервано не до конца". Новый код, который выставляет статус вручную (а не через уже существующий хелпер типа `_advance_series_run`), должен сверяться с этой семантикой, а не просто ставить `"completed"`, потому что "ну как бы закончили". Пример бага: `room_close()` ставил `"completed"` для недоигранной серии (найдено и исправлено 2026-09-28).

9. **Редирект/доступ предполагает роль, которой может не быть.** "Хост, но не участник комнаты (`RoomPlayer`)" — осознанно допустимая в этом проекте роль ("модератор"). Любой новый код, который ведёт хоста туда же, куда обычного игрока (`gameplay:play`, создание `GameParticipant` и т.п.), должен явно закладывать этот случай (`is_player = any(p.user_id == user.id for p in room.room_players.all())`), а не просто считать хоста участником.

10. **Опечатки, которые `manage.py check` не ловит.** `{% elseif %}` вместо `{% elif %}` (`TemplateSyntaxError` только при рендере), `.total_second()` вместо `.total_seconds()`, ключи контекста с лишним пробелом (`"can_start_round  "`) при точном сравнении по ключу в другом месте (консьюмер, JS). `manage.py check` проверяет только объявление моделей/URL/импорты, не рантайм-пути — эти баги всплывают только при реальном вызове соответствующей ветки кода.

## Как использовать

При ревью диффа — пройди по всем 10 пунктам явно (можно прямо по списку, коротко: "применимо/не применимо/нашёл"), а не полагайся на то, что заметишь их между делом при обычном чтении кода. Совмещай с [[session-review]], если ревью делается по итогам сессии для обновления документации.
