# session-review

В этом проекте пользователь пишет код сам ([CLAUDE.md](../../../CLAUDE.md) — режим "консультант", не исполнитель). Документация (`CLAUDE.md` → раздел "Текущее состояние", `TODO.md`) обновляется по итогам каждой сессии/пачки коммитов, и почти всегда — постфактум, отдельным заходом. Этот скилл формализует то, как это обновление должно быть сделано, чтобы не расходиться по формату и не пропускать реальные баги.

## Шаги

1. **Найти точку отсчёта.** В `CLAUDE.md` заголовок `### Текущее состояние (на момент последнего обновления этого файла — YYYY-MM-DD)` — это дата последней синхронизации. Всё, что случилось после неё — предмет ревью, **из двух источников сразу, не либо/либо** (см. шаг 2).

2. **Собрать весь объём изменений — и закоммиченное, и рабочее дерево.** У этого проекта два разных рабочих сценария, и оба обычны:
   - Пользователь закоммитил (и, может, запушил) что-то сам, без Claude, между сессиями — как было 2026-09-24/28: `PR #7` смержен, ревью только постфактум.
   - Пользователь только что писал код вместе с Claude в этой же сессии, протестировал, и просит обновить `.md` **до** коммита — коммит с кодом и обновлёнными доками делается одним заходом уже после этого (обычный флоу пользователя).
   Проверяй оба источника каждый раз:
   ```
   git log --oneline <последний уже задокументированный коммит>..HEAD   # закоммиченное, но не задокументированное
   git status --short                                                    # есть ли вообще незакоммиченные изменения
   git diff                                                              # unstaged
   git diff --staged                                                     # staged, если что-то уже добавлено в индекс
   ```
   Если не уверен, какой коммит уже задокументирован — сверься с последней записью в `CLAUDE.md`/`TODO.md` (там обычно указаны конкретные хэши или номер PR) и с `git log --oneline -30`, чтобы увидеть merge-коммиты/PR. Если `git status`/`git diff` пустые — просто нет незакоммиченных изменений, это нормально, ревьюй только историю коммитов.

3. **Прочитать весь собранный материал целиком**, не только commit message/список изменённых файлов:
   ```
   git show --stat <hash>   # что вообще менялось в коммите
   git show <hash>          # полный дифф коммита
   git diff -- <path>       # полный дифф незакоммиченного, если git diff целиком слишком большой
   ```
   Commit message пользователя описывает *намерение* ("host can view results of other players"), а не обязательно корректность реализации — самому нужно прочитать код. Для незакоммиченного источника имени/сообщения ещё нет вообще — единственный источник контекста - сам дифф.

4. **Искать реальные баги по ходу чтения**, а не просто пересказывать дифф. В частности:
   - Загрузи и примени чек-лист [[pitfalls-check]] (`.claude/skills/pitfalls-check/SKILL.md`) — там перечислены классы багов, которые в этом проекте уже случались несколько раз (null-FK без проверки, `.update()` вместо `.save()`, `RelatedManager` без `.all()` и т.д.). Пример находки этим способом: `gameplay/views.py::result()` — `session.room.host` без проверки на `None`, `AttributeError` на любом соло-раунде (сессия от 2026-09-24, найдено 2026-09-28).
   - Проверяй *предположения* кода о nullable-полях, порядке выполнения ветвлений (host/player, is_completed/in_progress/abandoned), семантике статусов, введённых в более ранних сессиях (не изобретай статус заново — сверься, как он уже используется в других местах кода).
   - Не полагайся на `manage.py check` — он не ловит большинство таких багов (ошибки времени выполнения, а не импорта/объявления моделей).

5. **Собрать находки и написать секцию**, следуя уже установленному в файлах формату:

   **В `CLAUDE.md`** (перед `## История сессий`, внутрь "Текущее состояние"):
   - Один новый bullet вида `- **Сессия от YYYY-MM-DD (ветка/PR, если есть): краткое название.** Кто писал код (по умолчанию — пользователь сам, Claude только ревьюил постфактум).`
   - Дальше — подпункты по каждой смысловой правке: что сделано, зачем, какие файлы/функции. Конкретные имена функций/файлов в бэктиках, обязательно `file:line` там, где это помогает быстро найти место.
   - Если баг не закрыт на момент записи — явно пометить (например, отдельным подпунктом "Найденный при ревью баг, не закрыт: ..."). Как только пользователь чинит — эта же запись правится на "исправлен пользователем DATE: ..." с итоговым диффом, а не создаётся новая запись рядом (сравни, как это сделано в существующих записях 2026-09-24/2026-09-28 в файле).
   - Обновить дату в заголовке `### Текущее состояние (... — YYYY-MM-DD)` на сегодняшнюю (дату ревью), даже если сами коммиты старше.
   - Для незакоммиченного материала не выдумывай хэш/номер PR — пиши просто "не закоммичено на момент ревью" или вообще без указания источника, дата всё равно сегодняшняя.

   **В `TODO.md`** (в конец файла, перед этим — не забыть дописать intro-предложение в самом начале файла, там ведётся сквозная сводка "обновлено по сессии от ..."):
   - Новый `## Найдено при сессии от YYYY-MM-DD (...)` с коротким пояснением, кто писал код и в каком режиме шло ревью (постфактум / по ходу).
   - Список `- [ ]`/`- [x]` находок, тем же стилем, что и во всех предыдущих разделах файла (смотри соседние разделы как образец — там всегда: что сломано, почему, где именно, что нужно/было сделано для фикса).

6. **Не трогай `CLAUDE_HISTORY.md` без явной просьбы.** По тексту самого `CLAUDE.md` новые сессионные записи в теории должны уезжать туда (файл `CLAUDE.md` растёт и должен оставаться компактным), но по факту практика последних сессий — писать прямо в "Текущее состояние" `CLAUDE.md`. Если раздел "Текущее состояние" разрастается и это становится заметно — скажи об этом пользователю прямым текстом и предложи перенести часть старых записей в `CLAUDE_HISTORY.md`, не делай это молча.

7. **Прежде чем писать в файлы — покажи находки пользователю в чате** (особенно если нашёл незакрытый баг) и дай короткую сводку. Само редактирование `.md`-файлов делай сразу (это документация, а не код — но если по ходу ревью всплыл баг в *коде*, который тянет на исправление, не чини его сам без запроса, только предложи, как обычно в этом проекте).
