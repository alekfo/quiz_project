# safe-cache-test

## Почему это отдельный скилл

`CACHES['default']` в этом проекте — `FileBasedCache` с `LOCATION = '/tmp/django_cache_quiz_project'` (`quiz_project/settings.py`). Это файлы на диске, общие для **любого** процесса, читающего те же настройки: `manage.py runserver`, `manage.py shell`, тестовый `Client()`. Все они при локальном тестировании резолвят IP в `127.0.0.1` — то есть пишут в один и тот же ключ кэша.

Уже происходивший инцидент: проверка регистрации через `manage.py shell` + `Client()` инкрементировала `register_attempts_127.0.0.1` до лимита ещё до того, как пользователь успел попробовать зарегистрироваться в браузере по-настоящему — первая же реальная попытка сразу получала "Слишком много попыток..." (см. `CLAUDE.md`/`TODO.md`, сессия про регистрацию).

## Механика rate-limit в этом проекте

- `users/views.py`: `_LOGIN_RATE_LIMIT = 3`, `_REGISTER_RATE_LIMIT = 3` (попыток в час, `timeout=3600`).
- Ключи кэша: `login_attempts_{ip}` (инкрементируется только на **неудачный** логин, `RateLimitedLoginView.form_invalid`), `register_attempts_{ip}` (инкрементируется на **любой** POST на `register()`, включая успешный — это известная асимметрия, см. `TODO.md`).
- `{ip}` при локальном тестировании (shell, `Client()`, `runserver` на localhost) почти всегда `127.0.0.1`.

## Что делать перед проверкой через shell/Client()

1. **Спросить/проверить, не запущен ли параллельно `runserver` пользователя.** Если да и пользователь может через несколько минут сам попробовать войти/зарегистрироваться в браузере — предупреди явно, что проверка через shell повлияет на его собственные попытки в браузере (общий кэш), и предложи альтернативу (см. ниже).

2. **Предпочитать не трогать реальные `login_attempts_*`/`register_attempts_*` ключи вообще**, если это возможно:
   - Проверять логику без реального HTTP-цикла (например, читать код `form_invalid`/`register()` и рассуждать, а не гонять реальные POST-запросы), когда вопрос не требует живого воспроизведения.
   - Если нужен именно живой прогон — предпочесть отдельный `python manage.py shell` со **своим** временным `CACHES`-оверрайдом (`django.test.override_settings` или временная замена `LOCATION` на другой файл) вместо продакшен-конфигурации из `settings.py`, чтобы физически не пересекаться с файлами, которые читает `runserver`.

3. **Если всё же используешь общий кэш** (например, тестовый `Client()` из `manage.py shell` без переопределения `CACHES`) — запомни, какие ключи трогаешь, и после теста явно удали именно их:
   ```python
   from django.core.cache import cache
   cache.delete('login_attempts_127.0.0.1')
   cache.delete('register_attempts_127.0.0.1')
   ```
   **Не вызывай `cache.clear()`** — он чистит вообще всё, что лежит в файловом кэше, включая то, что могло быть записано туда чем-то ещё не связанным с rate-limit (в текущем проекте `CACHES` используется только под rate-limit, но это может измениться — точечный `delete` безопаснее по умолчанию).

4. **Если пользователь сообщает "не могу войти/зарегистрироваться"** — прежде чем искать баг в форме/вьюхе, спроси или проверь, не проводилось ли недавно (в этой или соседней сессии) ручное тестирование этого эндпоинта через shell — это первая по вероятности причина, не логическая ошибка в коде.

## После любой проверки

Сообщи пользователю явно, какие ключи кэша были тронуты и очищены ли они — не оставляй это молчаливым побочным эффектом.
