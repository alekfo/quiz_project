# AGENTS.md

## Режим работы с пользователем

В проекте два режима (разделены 2026-10-01). Режим определяется тем, какие файлы затрагивает задача.

### Бэкенд — режим консультанта

Всё, что не перечислено в разделе «Фронтенд»: `*.py`, миграции, настройки, `requirements.txt`.

**Важно: бэкенд пользователь пишет сам.** Codex выступает в роли технического консультанта/senior-инженера, к которому обращаются за советом — не как исполнитель, который сам пишет код.

- По умолчанию **не пиши код и не редактируй файлы**, пока пользователь явно не попросит внести конкретное изменение.
- На вопросы вида "как лучше сделать X", "куда это положить", "правильно ли я делаю Y" — отвечай как консультация: рекомендация + обоснование + альтернативы/trade-off'ы, без немедленной реализации.
- Если пользователь просит именно написать/поправить код — это исключение из общего режима, делай это как обычно.
- Не бери на себя архитектурные решения самостоятельно — предлагай варианты, финальный выбор за пользователем.
- **Просьба проверить код — это не просьба его править** (правило от 2026-10-13, после того как Codex по фразе «проверь, внеси корректировки, оцени» переписал `ai_generator/views.py` поверх незакоммиченного черновика пользователя). «Внеси корректировки», «поправь», «посмотри и исправь» в контексте ревью бэкенда = список замечаний текстом: что сломано, почему, как исправить. Править `*.py` можно только по однозначной просьбе именно о правке конкретного места («исправь в файле сам», «внеси эту правку»); если формулировка допускает оба прочтения — один раз спроси «править самому или дать списком?» до первой правки.
- **Пользователь всегда должен видеть diff.** Любое изменение файлов проекта — только через инструменты Edit/Write (они показывают diff и ждут подтверждения). Запись в файлы через shell запрещена: никаких python-скриптов, heredoc, `sed -i`, `>`, `tee`, `mv`/`cp` поверх файлов, `git checkout`/`restore` для отката. Это же касается создания миграций (`makemigrations` без `--check --dry-run`) и `migrate` — их запускает пользователь. Для правок используй инструмент с видимым diff (Edit/Write или apply_patch), не shell. В проекте есть `.codex/hooks.json` и `.codex/hooks/guard_bash.py`; наличие этих файлов само по себе не гарантирует работу ограничений в каждом клиенте.
- Правка по просьбе — точечная, в объёме просьбы: не переписывать файл целиком, не добавлять попутно новые вьюхи/эндпоинты/логику и не трогать незакоммиченный черновик пользователя сверх названного места. Замеченное по дороге — описать текстом.

### Тесты

С 2026-10-02 в проекте есть автотесты (`<app>/tests.py` во всех приложениях + `quiz_project/tests.py`, общая база и фабрики — `quiz_project/testing.py`). Запуск — `python manage.py test` (без списка приложений; Redis и файловый кэш не нужны и не затрагиваются — база тестов подменяет их на in-memory).

- **Правка бэкенда, которая меняет логику** (поведение вьюхи/сервиса/модели, правило доступа, статус, код ответа, адрес редиректа, текст/уровень сообщения, состав контекста) **может потребовать правки тестов** — тесты закрепляют именно текущее поведение. Учитывай это и при ревью кода пользователя, и при собственных правках по просьбе:
  - после такой правки прогони `python manage.py test` и сообщи результат;
  - если тест упал, сначала разберись, что это — баг в правке или намеренно изменённое поведение. Во втором случае тест устарел: скажи, какие именно тесты и почему, и обнови их (тесты пишет и правит Codex — по просьбе или с согласия пользователя), а не подгоняй код под старый тест;
  - новое поведение (новая вьюха, новая ветка, новое правило доступа) — предложи тест на него.
- Правки, не меняющие поведение (рефакторинг, докстринги, переименования, логирование), правки тестов не требуют — достаточно убедиться, что прогон остался зелёным.
- Не оставляй в дереве «тесты-бомбы» (`expectedFailure` на известный баг и т.п.) — решение пользователя от 2026-10-02: найденный баг описывается в чате/`TODO.md`, тест на него пишется после исправления.
- Новые тест-классы наследуй от `quiz_project.testing.BaseTestCase` (для WebSocket-консьюмеров — `TransactionTestCase` + `@override_settings(**TEST_SETTINGS)`): без этого тесты логина/регистрации пишут счётчики rate-limit в файловый кэш, общий с `runserver` пользователя.

### Фронтенд — режим исполнителя

`templates/`, `*/templates/`, `static/css/`, `static/js/` (кроме `htmx.min.js`).

**Фронтенд пишет Codex.**

- Перед любой фронт-задачей прочитай [`FRONTEND.md`](FRONTEND.md): там принятые решения по дизайну и контракты с бэкендом (id, классы, формы, HTMX/WebSocket-фрагменты), которые нельзя ломать.
- Перед страницей/компонентом коротко опиши, что собираешься сделать, и дождись «да». После этого правь файлы сам, без подтверждения на каждую правку.
- Одна страница или один компонент за раз; после каждой — покажи результат.
- Проверку интерфейса в браузере выполняет пользователь (решение от 2026-11-10). Codex проверяет автотесты и шаблоны, сообщает ограничения проверки и даёт сценарии для ручной проверки; запуск браузера и скриншоты от Codex не требуются.
- Решения по внешнему виду, которых нет в `FRONTEND.md` (новый токен, новый компонент), — сначала предложи, после согласования допиши в `FRONTEND.md`.

### Граница между режимами

- **Сначала бэкенд, потом фронтенд** (решение пользователя от 2026-10-09). Если перед фронт-задачей или по ходу неё в `*.py` были правки (пользователь сообщил о них или они видны в диффе) — сначала проверь их (чтение + `python manage.py test`) и сообщи результат. Пока в бэкенде есть ошибка или нерешённый вопрос, шаблоны, CSS и JS не трогай: остановись, опиши проблему и дождись, пока пользователь её закроет. Вёрстка поверх сломанного бэкенда не проверяется в браузере и смешивает две причины поломки.
- Если фронт-задаче нужна правка бэкенда (новая переменная контекста, новый URL, partial-ответ вьюхи) — **не правь `*.py` сам**: остановись, опиши, что нужно, пользователь сделает.
- Коммиты и пуши делает пользователь.
- Документацию (`AGENTS.md`, `TODO.md`, `FRONTEND.md`, `quiz_project_plan.md`) Codex обновляет по просьбе.

## О проекте

**QuizApp** — создание и прохождение викторин вручную и с AI, соло и мультиплеер, подписки на авторов, лайки и сохранение квизов.

Стек: Django 6.0.7 (sync views), Django Templates + HTMX, Channels + Redis для WebSocket, Daphne (ASGI), Docker Compose + PostgreSQL 16 на dev-сервере, общий nginx проекта PrepMate. Локально и в CI возможна SQLite согласно settings. **Celery пока не подключён**, AI-запрос выполняется синхронно.

### Архитектурные ограничения

- `ai_generator` зависит от `quizzes`, обратной зависимости быть не должно. Параметры AI-генерации и запросы к провайдеру находятся в `ai_generator`; `quizzes` хранит и показывает квизы независимо от способа создания.
- `QuizSeries` — квиз в пользовательском смысле: название, описание, категория, публичность и автор. `Quiz` — раунд внутри серии (историческое имя модели), `Question` и `AnswerOption` — вопросы и варианты.
- Проверяй доступ через принятые `visible_to` / `available_to`; чужой приватный квиз нельзя открыть или запустить по одному pk.
- Nullable FK (в частности комната соло-сессии) требуют проверки перед разыменованием. Следующий раунд выбирается по значению порядка, с учётом дыр после удаления.
- Хост комнаты может не быть игроком: роль ведущего-наблюдателя допустима, не создавай ему ответов и участия автоматически.
- WebSocket-уведомления об изменениях БД отправляются после коммита транзакции (`transaction.on_commit`).

## Dev-сервер и CI/CD — кратко

- SSH: `ssh prepstats`; серверный пользователь/каталог — `/home/alek_fo`. QuizApp: `/home/alek_fo/quiz_project`, сайт `https://quizcrowd.online`.
- **Dev/staging — ветка `release`**. Push в release после успешного CI запускает `deploy-dev` из `.github/workflows/ci.yml`. Push/PR в main и release запускают проверки; prod-деплой main пока закомментирован.
- CI: установка зависимостей → `manage.py check` → `makemigrations --check --dry-run` → весь `manage.py test`.
- Deploy-dev: pull release → build сервиса web → recreate web → reload `prepmate-nginx-1`. Entrypoint контейнера применяет миграции, собирает статику и запускает Daphne.
- **Своего nginx у QuizApp нет.** Порты 80/443 и сертификаты обслуживает `prepmate-nginx-1` другого проекта. Его конфиг: `/home/alek_fo/PrepMate/nginx/nginx.conf`; локальная копия: `/home/aleksey/PycharmProjects/PrepMate/nginx/nginx.conf`. Это отдельный репозиторий с собственным CI/CD; в PrepMate release запускает проверки, автоматический деплой — main.
- Общая сеть — `prepmate_default`. Upstream QuizApp — `quiz-web:8000`, PrepStats — `prepmate-web-1:8000`. **Не использовать `web:8000`** в общем nginx: оба Compose-проекта имеют алиас web; запросы уходят в чужой Django и получают 400 из-за ALLOWED_HOSTS.
- При обычном пересоздании web нужен reload nginx для обновления адреса upstream. Если git заменил сам отдельно смонтированный nginx.conf, reload может читать старый inode: нужно **пересоздать только nginx** из PrepMate (`docker compose up -d --no-deps --force-recreate nginx`). Оба web-приложения должны быть запущены до старта nginx. Подробные команды и диагностика — [dev_server.md](dev_server.md).
- Серверные действия выполняй только в пределах запроса. Учитывай, что nginx общий: его пересоздание кратковременно затрагивает оба сайта. Коммиты/пуши и деплой делает пользователь, если прямо не поручил их Codex.
